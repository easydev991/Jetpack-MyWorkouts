## Этап 3. Инжектируемый таймаут подписки (property-путь) — выполнен

Было: LiveUpdate-тесты (~40 c на 7 тестов) пережидали реальный
5-секундный `WhileSubscribed(SUBSCRIPTION_TIMEOUT_MS)`, зашитый в 10
ViewModel приватной константой, и ждали фикс-сном `delay(5_300L)`.
Решение — property-путь: таймаут читается VM из system property
с дефолтом `5_000`; androidTest задают property в процессе приложения,
поэтому фабрики VM, `RootScreen` и `MainActivity` не тронуты,
androidx.test в прод-зависимости не появился.

- [x] Хелпер `ui/viewmodel/SubscriptionTimeout.kt` (property
  `myworkouts.subscription_timeout_ms`, fallback 5_000);
  `defaultSubscriptionTimeoutMs()` в `WhileSubscribed(...)` в 10 VM;
  JVM-тест покрывает fallback-ветку (override — e2e через правило).
- [x] Три LiveUpdate-класса: общее правило `SubscriptionTimeoutRule`
  (`@ClassRule`, property `100` на тест-класс, сброс после), сон
  `5_300` → `300` мс; ассерты и сценарии не тронуты.
- [x] Замер: LiveUpdate 32.3 → 14.4 c (дальше не сжимается — ~1–3 c
  постоянного запуска/навигации), 0 падений.

## Этап 4 (опционально, только если 1–3 мало). Шардирование на 2 эмулятора

Самый большой рычаг (≈ ×1.8), но второй AVD — это ещё ~2–3 GB RAM и ядра
CPU. На ноутбуке допустимо **только два** параллельных устройства.

- [ ] 4.1 Замерить свободную RAM/CPU при двух одновременно запущенных AVD;
  если ноутбук дышит — продолжать, нет — остановиться на этапах 1–3.
- [ ] 4.2 Включить Gradle Managed Devices: объявить Managed-устройство в
  `testOptions.managedDevices` в `app/build.gradle.kts` (не тесты); число
  шардов — экспериментальным флагом
  `android.experimental.androidTest.numManagedDeviceShards=2` в
  `gradle.properties` (это не DSL-свойство). Ручной split (два AVD +
  `numShards=2`/`shardIndex` в двух Gradle-вызовах) — не основной путь:
  параллельные вызовы Gradle конкурируют за лок проекта и выбор
  adb-устройства; fallback, только если Managed Devices не подойдёт —
  обсуждается отдельно.
- [ ] 4.3 A/B замер и проверка стабильности 3–5 прогонов подряд (шарды
  вносят flaky-риск на слабом железе). При flaky — откат к этапам 1–3.

**Риск:** средний (параллелизм на ограниченном железе). **Выигрыш:**
≈ ×1.8 по device-времени: 172.0 c → ~95 c, wall ≈ 3:18 → ~2:15 поверх
выполненных этапов 1–3 — оценка по device-времени; GMD поднимает свои
AVD из снапшота (не холодный бут), но оверхед на параллельные
устройства в wall-время проверить в 4.3.

## Не делаем (осознанно)

- Параллельный executor внутри одного AVD — flaky по общему
  приложению/БД.
- Больше 2 устройств/шардов — нагружает ноутбук.
- `org.gradle.workers.max` вручную — вмешательство в пул воркеров Gradle
  без нужды (риск нестабильности сборки).
- Удаление/группировка «медленных» тестов, усечение `EntryCreateScreenTest`
  и т.п. — любая потеря покрытия запрещена условием задачи.
- Ассерты LiveUpdate-тестов не переписывать: они фиксируют реальное
  поведение `WhileSubscribed`; в этапе 3 менялись только константа
  таймаута и следующий за ней фикс-сон, логика проверки — нет
  (правило остаётся для будущих правок этих тестов).
