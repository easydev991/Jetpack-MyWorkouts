# app-review Specification

## Purpose

Позволяет пользователям rustore-сборки оценить приложение через нативную форму RuStore In-App Review SDK — по автоматическим milestone-триггерам при создании записей о выполнении упражнений. Кнопка «Оценить приложение» остаётся без изменений (открывает страницу отзывов, спека `more-screen`) и SDK не вызывает.

## Requirements

### Requirement: Гейтинг review-функциональности по flavor

Система MUST выполнять автоматические запросы оценки ТОЛЬКО на rustore-сборке (`BuildConfig.RUSTORE_FEATURES == true`). На github-сборке авто-запросы MUST NOT инициироваться ни при каких условиях, и счётчик созданных записей MUST NOT вестись.

#### Scenario: Счётчик и авто-запросы только на rustore-сборке

- **WHEN** пользователь создаёт записи о выполнении упражнений на rustore-сборке (`BuildConfig.RUSTORE_FEATURES == true`)
- **THEN** система ведёт счётчик созданных записей и планирует авто-запросы по milestone-порогам

#### Scenario: GitHub-сборка без review-функциональности

- **WHEN** пользователь создаёт записи на github-сборке (`BuildConfig.RUSTORE_FEATURES == false`)
- **THEN** счётчик не ведётся, и никакие действия пользователя в приложении не приводят к показу формы оценки

### Requirement: Отсутствие вмешательства в SDK-форму

Система MUST NOT отображать собственные UI-элементы поверх нативной формы оценки или по её краям и MUST NOT закрывать форму принудительно. После завершения флоу система MUST NOT показывать какие-либо дополнительные собственные формы, связанные с оценкой, внутри приложения. Кнопка «Оценить приложение» экрана «Ещё» SDK не вызывает — её поведение определяется спекой `more-screen` и не меняется.

#### Scenario: Никаких собственных элементов вокруг формы

- **WHEN** нативная форма оценки отображена
- **THEN** система не добавляет собственных диалогов, оверлеев или подсказок поверх формы и по её краям

#### Scenario: Отсутствие дополнительных форм после завершения

- **WHEN** нативная форма завершилась (успех или ошибка)
- **THEN** система возвращает пользователя к текущему экрану без собственных диалогов, тостов или других собственных форм, связанных с оценкой

### Requirement: Milestone-триггеры автоматического запроса

Система MUST вести кумулятивный счётчик успешно созданных записей о выполнении упражнений как источник авто-триггеров с порогами `[1, 5, 15]`: при достижении порога MUST выбираться наивысший достигнутый milestone, ещё не пройденный за жизнь установки. Редактирование существующей записи счётчик MUST NOT увеличивать. Записи, восстановленные импортом бэкапа, счётчик MUST NOT увеличивать. После прохождения всех трёх milestone-ов авто-запросы MUST NOT инициироваться.

#### Scenario: Первая созданная запись

- **WHEN** пользователь успешно сохраняет новую запись, и счётчик становится равен 1
- **THEN** система планирует авто-запрос оценки для milestone 1

#### Scenario: Пятая и пятнадцатая созданные записи

- **WHEN** счётчик успешно созданных записей достигает 5, а затем 15
- **THEN** система планирует авто-запрос для milestone 5, а затем для milestone 15

#### Scenario: Редактирование не считается

- **WHEN** пользователь редактирует и сохраняет существующую запись
- **THEN** счётчик созданных записей не изменяется, авто-запрос не планируется

#### Scenario: Импорт бэкапа не считается

- **WHEN** пользователь импортирует бэкап, восстанавливающий записи
- **THEN** счётчик созданных записей не изменяется, авто-запрос не планируется

#### Scenario: Все milestones пройдены

- **WHEN** milestones 1, 5 и 15 уже пройдены, и пользователь создаёт новые записи
- **THEN** система больше не планирует авто-запросы оценки

### Requirement: Ограничение частоты авто-запроса

Система MUST инициировать не более одного авто-запроса оценки за сессию приложения (от запуска до завершения процесса). Milestone MUST помечаться пройденным в момент запуска SDK-флоу, независимо от того, была ли форма фактически показана (лимит отображений регулируется на стороне RuStore и системой не отслеживается).

#### Scenario: Два порога в одной сессии

- **WHEN** в одной сессии пользователь создаёт записи, приводящие к достижению двух разных milestone-ов, и авто-запрос для первого уже запускался
- **THEN** второй авто-запрос в этой сессии не запускается; второй milestone остаётся непройденным и планируется при следующем создании записи (возможно, в новой сессии приложения)

#### Scenario: Пройденный milestone не повторяется

- **WHEN** авто-запрос для milestone запускался ранее (форма фактически не показалась из-за лимита на стороне RuStore)
- **THEN** этот milestone больше не запускает авто-запрос

### Requirement: Непоказанный pending не перезаписывается

Если авто-запрос уже запланирован (pending), но ещё не показан, достижение более высокого milestone MUST NOT приводить к перезаписи pending или планированию нового авто-запроса. Более высокий milestone MUST остаться непройденным и будет запланирован при следующем создании записи после показа текущего pending.

#### Scenario: Новый milestone при непоказанном pending

- **WHEN** авто-запрос запланирован (pending), но ещё не показан, и пользователь создаёт записи, приводящие к достижению более высокого milestone
- **THEN** запланированный (pending) milestone не перезаписывается и новый авто-запрос не планируется; более высокий milestone остаётся непройденным и будет запланирован при следующем создании записи после показа текущего pending

### Requirement: Отложенный показ авто-запроса

Система MUST показывать нативную форму по авто-триггеру не в момент создания записи, а после возврата на главный экран списка тренировок с задержкой около 0.8 секунды. Если сессия завершилась до показа, milestone MUST остаться непройденным, а запланированный (pending) milestone MUST сохраниться между запусками приложения — авто-запрос показывается при следующем возврате на главный экран.

#### Scenario: Показ после возврата на главный экран

- **WHEN** авто-запрос запланирован, и пользователь вернулся на главный экран списка тренировок
- **THEN** — если лимит сессии не исчерпан (авто-запрос в текущей сессии ещё не выполнялся, см. «Ограничение частоты авто-запроса») — примерно через 0.8 секунды система запускает SDK-флоу и показывает нативную форму

#### Scenario: Приложение закрыто до показа

- **WHEN** сессия завершилась между планированием авто-запроса и его показом
- **THEN** milestone остаётся непройденным, запланированный (pending) milestone сохраняется, и при следующем возврате на главный экран списка тренировок авто-запрос показывается — новые созданные записи для этого не требуются

### Requirement: Тихая обработка ошибок авто-запроса

В авто-режиме (запрос не инициирован пользователем) при любой ошибке SDK-флоу — подготовка данных или показ формы — система MUST продолжать работу без отображения ошибок, сообщений или фолбэка на браузер. Любая такая ошибка MUST фиксироваться только аналитическим событием (см. «Аналитика review-флоу»).

#### Scenario: Ошибка SDK при авто-запросе

- **WHEN** авто-запрос инициирован, но SDK-флоу завершился ошибкой (например, исчерпан лимит отображений)
- **THEN** интерфейс приложения не меняется: никаких сообщений пользователю и переходов в браузер нет

#### Scenario: RuStore не установлен

- **WHEN** авто-запрос инициирован, но RuStore не установлен (предпроверка установки в авто-пути не выполняется, отсутствие RuStore проявляется как ошибка подготовки данных)
- **THEN** система продолжает работу без ошибок и фолбэка на браузер; исход фиксируется только аналитическим событием

#### Scenario: Сбой хранилища счётчиков до SDK-флоу

- **WHEN** чтение хранилища счётчиков (например, `IOException` файла DataStore) завершилось ошибкой до инициализации SDK-флоу
- **THEN** ошибка обрабатывается тихим логом без аналитического события, и авто-запрос не инициируется

### Requirement: Персистентность и сброс счётчиков

Система MUST сохранять счётчик созданных записей, список пройденных milestone-ов и запланированный (pending) milestone между запусками приложения. При полном удалении всех данных пользователем (экран «Данные приложения», действие «Удалить все данные» — спека `app-data-management`) система MUST сбрасывать счётчик, пройденные milestones и запланированный (pending) milestone, после чего авто-запросы начинаются заново с milestone 1 с учётом лимита сессии («Ограничение частоты авто-запроса»).

#### Scenario: Прогресс переживает перезапуск

- **WHEN** пользователь создаёт записи, закрывает приложение и запускает его снова
- **THEN** счётчик, список пройденных milestone-ов и запланированный (pending) milestone сохраняются; созданные ранее записи не приводят к повторному авто-запросу для пройденных milestone-ов

#### Scenario: Полное удаление данных сбрасывает счётчики

- **WHEN** пользователь выполняет действие «Удалить все данные» на экране «Данные приложения»
- **THEN** счётчик созданных записей, пройденные milestones и запланированный (pending) milestone сбрасываются; следующая созданная запись снова приводит к авто-запросу для milestone 1, если лимит сессии не исчерпан (авто-запрос в текущей сессии ещё не выполнялся); при исчерпанном лимите — при следующем создании записи в новой сессии приложения

### Requirement: Аналитика review-флоу

Система MUST логировать через существующий механизм аналитики (событийная модель `AnalyticsEvent`) события авто-запроса review-флоу (milestone-триггер) с исходом: «форма показана» при успешном показе формы, «ошибка» с типом ошибки SDK — при любой ошибке (см. «Тихая обработка ошибок авто-запроса»). Состав параметров события фиксирован: исход и (при ошибке) тип ошибки SDK; номер milestone в событие не входит.

#### Scenario: Успешный показ логируется

- **WHEN** авто-запрос запущен, и нативная форма показалась
- **THEN** система логирует событие с исходом «форма показана»

#### Scenario: Ошибка логируется с типом

- **WHEN** авто-запрос запущен, но фаза подготовки данных или показа формы завершилась ошибкой SDK (например, исчерпан дневной лимит отображений)
- **THEN** система логирует событие с исходом «ошибка» и типом ошибки SDK
