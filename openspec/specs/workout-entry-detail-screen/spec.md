# workout-entry-detail-screen Specification

## Purpose

Детальный экран записи о выполнении: полноэкранный просмотр одной записи по
идентификатору с действиями «Изменить»/«Удалить», реактивной актуализацией
данных и стандартной стековой навигацией с главного экрана. Заменяет
всплывающую карточку деталей главного экрана.

## Requirements

### Requirement: Открытие экрана деталей записи

Обычный тап по строке записи и пункт «Открыть» контекстного меню SHALL
открывать детальный экран этой записи — навигационную дестинацию
`entry_detail/{entryId}`, переходом поверх главного экрана. Строка записи
SHALL предоставлять локализованное ru/en accessibility-действие «Показать
детали»: активация действия из меню действий скринридера SHALL открывать
детальный экран (тот же переход, что тап). Тап по строке при открытом
контекстном меню SHALL закрывать только меню, без перехода.

#### Scenario: Тап по строке открывает экран деталей

- **WHEN** пользователь выполняет обычный тап по строке записи
- **THEN** открывается детальный экран этой записи
- **AND** главный экран остаётся в стеке под детальным экраном
- **AND** выделение строки попапом не появляется (строка выглядит обычно)

#### Scenario: Пункт «Открыть» открывает экран деталей

- **WHEN** пользователь выполнил длинное нажатие на строку записи и выбрал
  пункт «Открыть» контекстного меню
- **THEN** контекстное меню закрывается
- **AND** открывается детальный экран этой записи — тот же переход, что по тапу

#### Scenario: A11y-действие открывает экран деталей

- **WHEN** пользователь скринридера активирует на строке записи
  accessibility-действие «Показать детали» / "Show details"
- **THEN** открывается детальный экран этой записи
- **AND** открытое контекстное меню закрывается

#### Scenario: Тап при открытом меню закрывает только меню

- **WHEN** контекстное меню открыто и пользователь выполняет тап по строке
- **THEN** контекстное меню закрывается
- **AND** детальный экран не открывается

### Requirement: Состав экрана деталей записи

Экран SHALL состоять из `TopAppBar` («Детали записи», стрелка назад, actions
«Изменить»/«Удалить» — только при загруженной записи) и контента записи,
расположенного по центру свободного места без Card-фона сверху вниз: иконка
упражнения, название, значение записи, дата/время выполнения, комментарий
при наличии. Стили элементов и правила иконки/значения — по правилам
главного экрана (сценарии ниже).

#### Scenario: Стили элементов экрана

- **WHEN** экран отображает элементы записи
- **THEN** название упражнения набрано `titleLarge` по центру
- **AND** значение крупно (`headlineMedium`, цвет `primary`) в одну строку:
  при нескольких подходах — «подходы × значение», при одном — только
  значение
- **AND** суффикс веса вида «(+ 5 кг)» из ресурса
  `entry_details_weight_suffix` локализован ru/en; при весе 0/`null`
  суффикс SHALL NOT отображаться
- **AND** известный номер иконки — иконка 24dp, `null`/неизвестный —
  иконка не отображается
- **AND** дата/время выполнения отображаются стилем `bodySmall` с цветом
  `onSurfaceVariant`; формат — день месяца, месяц, год, часы и минуты
  записи (например «20 сентября 2025, 18:30»)

#### Scenario: Значение с подходами и весом

- **WHEN** открыт экран записи: 4 подхода, 10 повторов, вес 5 кг
- **THEN** значение отображается крупно основным цветом в формате
  «4 х 10 (+ 5 кг)»

#### Scenario: Один подход без веса скрывает дефолты

- **WHEN** открыт экран записи: 1 подход, 12 повторов, без веса
- **THEN** значение отображается как «12» без количества подходов и весового
  суффикса

#### Scenario: Длительность на экране деталей

- **WHEN** открыт экран записи на время: 3 подхода по 20 секунд
- **THEN** значение отображается в формате «3 х 20 сек» без весового суффикса

#### Scenario: Дата и время отображаются всегда

- **WHEN** открыт экран любой записи
- **THEN** под значением отображаются дата и время выполнения записи
  (формат — по сценарию «Стили элементов экрана»)

#### Scenario: Комментарий отображается целиком

- **WHEN** открыт экран записи с комментарием длиннее двух строк
- **THEN** комментарий отображается полностью в тональном блоке
  `surfaceVariant` со скруглением — без обрезки и многоточия
- **AND** блок комментария растёт по содержимому без фиксированного
  ограничения высоты; при переполнении доступного места текст скроллится
  внутри блока, не выходя за пределы экрана

#### Scenario: Пустой комментарий не отображается

- **WHEN** открыт экран записи с комментарием `null` или blank
- **THEN** блок комментария не отображается

#### Scenario: Actions доступны только при загруженной записи

- **WHEN** экран находится в состоянии ошибки или загрузки
- **THEN** actions «Изменить»/«Удалить» в `TopAppBar` не отображаются
- **AND** стрелка назад отображается всегда

#### Scenario: Порядок и подписи actions

- **WHEN** `TopAppBar` экрана отображает действия
- **THEN** порядок элементов: стрелка назад, затем «Изменить», затем
  «Удалить» (как в референсе JetpackDays)
- **AND** стрелка и обе иконки имеют локализованные ru/en описания
  доступности

### Requirement: Состояния экрана и несуществующий id

Экран SHALL иметь три взаимоисключающих состояния: `Loading` (до первой
эмиссии данных), `Success` (данные записи) и `Error` (запись не найдена).
Для несуществующего идентификатора записи экран SHALL показывать заглушку
«Запись не найдена» — состояние `Error`, а не вечный `Loading`. Если запись
удалена из хранилища, пока экран открыт, экран SHALL показывать ту же
заглушку.

#### Scenario: Существующий id показывает запись

- **WHEN** экран открыт с идентификатором существующей записи
- **THEN** экран переходит из `Loading` в состояние с данными записи

#### Scenario: Несуществующий id показывает заглушку

- **WHEN** экран открыт с идентификатором, для которого записи в хранилище нет
- **THEN** отображается заглушка «Запись не найдена»
- **AND** вечной загрузки не происходит

#### Scenario: Удалённая запись показывает заглушку

- **WHEN** запись удалена из хранилища, пока экран открыт
- **THEN** экран показывает заглушку «Запись не найдена»

### Requirement: Актуализация данных экрана

Данные экрана SHALL браться из реактивного потока записи по идентификатору
из слоя данных: при изменении записи экран SHALL отображать актуальные данные
без переоткрытия. Возврат с экрана редактирования после успешного сохранения
SHALL показывать на детальном экране свежие данные. При смене конфигурации
(поворот экрана) экран SHALL оставаться на записи с тем же идентификатором.

#### Scenario: Изменённая запись отображается актуально

- **WHEN** данные записи изменились в хранилище, пока экран открыт
- **THEN** экран отображает актуальные данные записи

#### Scenario: Возврат после сохранения показывает актуальные данные

- **WHEN** пользователь вернулся с экрана редактирования после успешного
  сохранения
- **THEN** детальный экран показывает обновлённые данные записи
- **AND** переоткрытие экрана для этого не требуется

#### Scenario: Поворот сохраняет данные

- **WHEN** экран открыт и происходит смена конфигурации (поворот)
- **THEN** экран остаётся открытым с данными той же записи

### Requirement: Удаление записи с экрана деталей

«Удалить» в `TopAppBar` SHALL открывать `AlertDialog` подтверждения в стиле
существующего алерта удаления главного экрана (состав — в сценарии ниже).
Запись SHALL удаляться только после подтверждения; после подтверждения экран
SHALL закрываться возвратом на главный экран (`popBackStack`) — без snackbar.
Отмена SHALL оставлять пользователя на детальном экране с записью. При ошибке
слоя данных запись SHALL NOT удаляться, экран и алерт остаются открытыми,
сбой SHALL доходить до репортёра сбоев.

#### Scenario: Состав алерта подтверждения

- **WHEN** пользователь нажал «Удалить» на детальном экране
- **THEN** показывается алерт с заголовком «Удалить запись?», текстом с
  названием упражнения записи
- **AND** подтверждающая кнопка «Удалить» набрана в цвете ошибки
- **AND** отменяющая кнопка — «Отмена»

#### Scenario: Подтверждение удаляет запись и возвращает на главный экран

- **WHEN** пользователь нажал «Удалить» и подтвердил удаление в алерте
- **THEN** запись удаляется из хранилища
- **AND** детальный экран закрывается, отображается главный экран
- **AND** удалённая запись отсутствует в списке записей

#### Scenario: Отмена остаётся на экране

- **WHEN** алерт подтверждения открыт и пользователь нажал «Отмена»,
  системный Back или тапнул вне алерта
- **THEN** алерт закрывается
- **AND** пользователь остаётся на детальном экране, запись не удалена

#### Scenario: Ошибка слоя данных не закрывает экран

- **WHEN** подтверждение удаления выполнено и слой данных вернул ошибку
- **THEN** запись остаётся в хранилище
- **AND** детальный экран и алерт остаются открытыми для повторной попытки

### Requirement: Переход на редактирование с экрана деталей

«Изменить» в `TopAppBar` SHALL открывать существующий экран записи в режиме
редактирования этой записи поверх детального экрана, без замены его в стеке.
Возвраты SHALL выполняться стандартным стеком: отмена редактирования SHALL
возвращать на детальный экран без изменений данных, успешное сохранение SHALL
возвращать на детальный экран с актуализированными данными. Редактирование
с главного экрана (контекстное меню) SHALL NOT меняться: отмена и сохранение
возвращают на главный экран.

#### Scenario: Изменить открывает редактирование поверх деталей

- **WHEN** пользователь нажал «Изменить» на детальном экране
- **THEN** переход выполняется на `Screen.EntryCreate.createRoute(entryId)`
- **AND** открывается экран записи в режиме редактирования с заголовком
  «Изменить запись» и формой, предзаполненной данными записи
- **AND** детальный экран остаётся в стеке под экраном редактирования

#### Scenario: Отмена возвращает на детали без изменений

- **WHEN** пользователь отменил редактирование (стрелка `TopAppBar`,
  системный Back или жест свайпа назад)
- **THEN** открывается детальный экран
- **AND** данные записи не изменились

#### Scenario: Сохранение возвращает на детали с обновлёнными данными

- **WHEN** пользователь изменил запись на экране редактирования и сохранил
- **THEN** экран редактирования закрывается возвратом на детальный экран
- **AND** детальный экран показывает обновлённые данные записи

#### Scenario: Редактирование с главного экрана возвращает на главный

- **WHEN** пользователь открыл редактирование из контекстного меню главного
  экрана и отменил или сохранил изменения
- **THEN** отображается главный экран
- **AND** детальный экран в стеке не участвует

### Requirement: Возврат с экрана деталей

Возврат с детального экрана на главный SHALL быть доступен стрелке назад
в `TopAppBar`, системной кнопке Back и жесту свайпа назад — все три способа
SHALL выполнять один и тот же возврат по стеку навигации. Кастомный
`BackHandler` на детальном экране SHALL NOT добавляться: экран не имеет
состояний, требующих перехвата системного назад. Единственный `BackHandler`
в связке экранов — существующий на экране записи (подтверждение ухода с
несохранёнными изменениями).

#### Scenario: Стрелка назад возвращает на главный экран

- **WHEN** пользователь нажал стрелку назад в `TopAppBar` детального экрана
- **THEN** открывается главный экран

#### Scenario: Системный Back возвращает на главный экран

- **WHEN** пользователь нажал системную кнопку Back или выполнил жест свайпа
  назад на детальном экране
- **THEN** открывается главный экран

#### Scenario: Системный Back из редактирования возвращает на детали

- **WHEN** открыт экран редактирования поверх детального и пользователь
  выполняет системный Back/жест (при отсутствии несохранённых изменений)
- **THEN** открывается детальный экран
- **AND** диалог подтверждения закрытия не показывается

### Requirement: Нижняя навигация скрыта на экране деталей

Нижняя панель навигации SHALL NOT отображаться на маршруте
`entry_detail/{entryId}` — на всём пути «главный → детали → редактирование».
Возврат на главный экран SHALL возвращать нижнюю навигацию.

#### Scenario: Бар не отображается на детальном экране

- **WHEN** активен маршрут детального экрана
- **THEN** нижняя панель навигации отсутствует в дереве композиции
- **AND** контент экрана использует освободившееся место

#### Scenario: Бар отсутствует на всём пути редактирования

- **WHEN** открыт экран редактирования, вызванный с детального экрана
- **THEN** нижняя панель навигации отсутствует на обоих экранах

#### Scenario: Бар возвращается на главном экране

- **WHEN** пользователь вернулся с детального экрана на главный
- **THEN** нижняя панель навигации снова отображается

### Requirement: Безопасные зоны экрана деталей

Приложение работает в режиме edge-to-edge, поэтому детальный экран SHALL
самостоятельно учитывать системные insets: `TopAppBar` SHALL отступать от
статус-бара, контент SHALL позиционироваться через padding `Scaffold`'a
и SHALL NOT заходить под статус-бар, системную панель навигации и display
cutout. Кастомные inset-схемы главного экрана (горизонтальный
`safeDrawing`-фильтр) SHALL NOT переноситься на детальный экран: нижнего
бара на экране нет, вертикальные insets учитываются полностью.

#### Scenario: Контент не под системными панелями

- **WHEN** детальный экран открыт на устройстве с жестовой навигацией и
  display cutout
- **THEN** `TopAppBar` не заходит под статус-бар
- **AND** контент и блок комментария не заходят под панель навигации и
  display cutout

### Requirement: Аналитика экрана деталей

Открытие детального экрана SHALL логировать `ScreenView` экрана
(`AppScreen.EntryDetailScreen`) через общий breadcrumbs-механизм навигации.
Открытие деталей (тап, пункт «Открыть» или a11y-действие «Показать
детали») SHALL логировать пользовательское действие `OPEN_ENTRY_DETAIL`. Переход на редактирование с детального экрана
SHALL логировать существующее действие `EDIT`; подтверждение удаления SHALL
логировать существующее действие `DELETE`.

#### Scenario: Открытие логирует ScreenView и действие открытия

- **WHEN** пользователь открыл детальный экран тапом, пунктом «Открыть»
  или a11y-действием «Показать детали»
- **THEN** логируется `ScreenView` экрана `AppScreen.EntryDetailScreen`
- **AND** логируется пользовательское действие `OPEN_ENTRY_DETAIL`

#### Scenario: Переход на редактирование логирует EDIT

- **WHEN** пользователь нажал «Изменить» на детальном экране
- **THEN** логируется существующее пользовательское действие `EDIT`

#### Scenario: Подтверждение удаления логирует DELETE

- **WHEN** пользователь подтвердил удаление записи с детального экрана
- **THEN** логируется существующее пользовательское действие `DELETE`
