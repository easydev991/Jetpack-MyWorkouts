# workout-data Specification

## Purpose

Персистентный слой данных тренировок: единый каталог упражнений
(стандартные + пользовательские) и записи о выполнении. Предоставляет
поиск, создание и редактирование данных для будущего UI-слоя, не зависит
от UI и сети (offline-only).

## Requirements

### Requirement: Единый каталог для стандартных и пользовательских упражнений

Пользовательские упражнения SHALL сохраняться в тот же каталог, что и
стандартные, с пометкой «создано пользователем». Для создания
упражнения SHALL требоваться название и категория; комментарий SHALL
быть опциональным. Каждое упражнение каталога SHALL иметь тип
измерения `measuredBy`, булевый флаг `isArchived` (по умолчанию
`false`) и системный идентификатор; тип и флаг SHALL сохраняться
вместе с упражнением и SHALL быть доступны при чтении каталога.

#### Scenario: Типы измерения REPS и TIME

- **WHEN** задаётся тип измерения упражнения каталога
- **THEN** используются `REPS` (упражнение на повторы) и `TIME`
  (упражнение на время); при создании пользовательского упражнения
  без явного указания типа применяется `REPS`

#### Scenario: Флаг isArchived и его представление в Room

- **WHEN** определяется хранение флага архивации в каталоге
- **THEN** `false` — упражнение активно и видно в каталоге; `true` —
  упражнение скрыто из каталога и доступно только через экран архива
- **AND** по умолчанию `isArchived = false` (новые и существующие
  упражнения — активные)
- **AND** в Room-сущности `ExerciseEntity` поле хранится как
  `INTEGER NOT NULL DEFAULT 0` через `@ColumnInfo(name =
  "is_archived", defaultValue = "0")`

#### Scenario: Идентификатор упражнения генерируется системой

- **WHEN** создаётся упражнение каталога
- **THEN** идентификатор упражнения генерируется системой

#### Scenario: Создание пользовательского упражнения

- **WHEN** пользовательское упражнение «Отжимания на турнике» категории PULL
  с комментарием «широкий хват» сохраняется
- **THEN** оно появляется в каталоге с пометкой «пользовательское»
  AND `isArchived = false` по умолчанию
- **AND** стандартные упражнения остаются неизменными

#### Scenario: Тип измерения по умолчанию при создании

- **WHEN** пользовательское упражнение сохраняется без явного указания
  типа измерения
- **THEN** упражнение сохраняется с `measuredBy = REPS`
  AND `isArchived = false`

#### Scenario: Создание упражнения «на время»

- **WHEN** пользовательское упражнение (например, «стойка на руках»)
  сохраняется с `measuredBy = TIME`
- **THEN** при чтении каталога упражнение возвращается с `measuredBy = TIME`
  AND `isArchived = false`

### Requirement: Комментарий упражнения хранится в каталоге

Каждое упражнение (стандартное и пользовательское) SHALL иметь опциональный
комментарий, описывающий упражнение. Редактирование комментария SHALL менять
единственную запись каталога; записи о выполнении SHALL продолжать видеть
актуальный комментарий через ссылку на упражнение, без собственных копий.

#### Scenario: Редактирование комментария стандартного упражнения

- **WHEN** комментарий упражнения «Подтягивания» меняется на
  «хват сверху, лопатки сведены»
- **THEN** изменена ровно одна строка каталога
- **AND** чтение упражнения по идентификатору возвращает новый комментарий

### Requirement: Поиск и сортировка каталога

Каталог SHALL предоставляться отсортированным: `is_custom DESC,
created_at DESC, name COLLATE NOCASE`; архивные упражнения — по той
же сортировке отдельным SQL-запросом. Фильтрация по подстроке
названия SHALL выполняться без учёта регистра. Архивные упражнения
(`isArchived = true`) SHALL NOT попадать в результат
`exercises(query)`.

#### Scenario: Сортировка архивных упражнений

- **WHEN** запрашиваются архивные упражнения
- **THEN** сортировка та же, что у активных (`is_custom DESC,
  created_at DESC, name COLLATE NOCASE`, name — без учёта
  регистра), отдельный SQL-запрос
- **AND** архивные упражнения доступны через отдельный метод
  `archivedExercises()`

#### Scenario: Поиск по подстроке

- **WHEN** запрашивается каталог с подстрокой «под»
- **THEN** возвращаются только активные упражнения с «под» в названии
  (например, «Подтягивания», «Подъёмы ног в висе»); архивные
  упражнения с «под» в названии НЕ попадают в результат
- **AND** результат отсортирован по `is_custom DESC, created_at DESC,
  name COLLATE NOCASE`

#### Scenario: Пустой запрос возвращает весь каталог

- **WHEN** запрашивается каталог с пустой подстрокой
- **THEN** возвращаются все упражнения активного каталога
  (`isArchived = false`); архивные упражнения НЕ попадают в
  результат
- **AND** архивные упражнения доступны через отдельный метод
  `archivedExercises()`

### Requirement: Запись о выполнении ссылается на упражнение каталога

Запись о выполнении SHALL хранить ссылку на упражнение каталога,
календарную дату выполнения (epoch millis) и плоские поля: количество
подходов, опциональные повторы, опциональный вес в кг, опциональную
длительность в секундах, опциональный комментарий. Ввод набора
подходов SHALL сохраняться одной записью, а не отдельной строкой на
подход. Текстовые подписи записей SHALL вычисляться из полей при
отрисовке и не храниться в базе.

#### Scenario: Одна запись на ввод «4×10 с весом»

- **WHEN** сохраняется ввод «4 подхода по 10 повторов с весом 5 кг»
  («4×10 с весом 5 кг»)
- **THEN** в базе создана ровно одна запись: подходы = 4, повторы = 10,
  вес = 5.0, а не отдельная строка на подход
- **AND** в MVP каждая создаваемая запись одиночная (без привязки к
  тренировке)

#### Scenario: Ссылка на существующее упражнение

- **WHEN** сохраняется запись со ссылкой на существующее упражнение
- **THEN** запись сохранена и читается вместе со ссылкой на упражнение

#### Scenario: Ссылка на несуществующее упражнение

- **WHEN** выполняется попытка сохранить запись с идентификатором
  упражнения, отсутствующим в каталоге
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

### Requirement: Валидация полей записи

Хранилище SHALL отклонять запись о выполнении при нарушении любого
правила валидации (перечень — в сценарии ниже), включая отсутствие
обязательного по типу измерения упражнения (`measuredBy`) значения.
Идентичные записи SHALL быть разрешены: дедупликация не выполняется.
Обнуляемость полей на уровне модели SHALL сохраняться (несоответствие
ловится валидацией, не типом); отсутствие веса (собственный вес) и
нулевой вес SHALL оставаться различимыми состояниями.

#### Scenario: Перечень правил валидации полей

- **WHEN** сохраняется запись, у которой количество подходов меньше
  1, или повторы указаны и меньше 1, или вес указан и меньше 0, или
  длительность указана и меньше 1, или повторы и длительность заданы
  одновременно, или запись привязана к тренировке (workoutId ≠ null —
  тренировки появятся в будущих изменениях)
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся
- **AND** каждая вставка идентичной записи создаёт отдельную строку
  со своим id

#### Scenario: Нулевое количество подходов

- **WHEN** выполняется попытка сохранить запись с подходами = 0
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Привязка к тренировке отклоняется

- **WHEN** выполняется попытка сохранить запись с workoutId ≠ null
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Отсутствие веса и нулевой вес различимы

- **WHEN** одна запись сохранена без веса, другая — с весом 0.0
- **THEN** при чтении обе записи различимы: у первой вес не задан,
  у второй равен 0.0

#### Scenario: Отсутствие повторов у упражнения на повторы

- **WHEN** сохраняется запись упражнения `measuredBy = REPS`
  без повторов (даже если длительность указана)
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Нулевое количество повторов отклоняется

- **WHEN** сохраняется запись с заданными повторами = 0
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Несовместимые поля отклоняются

- **WHEN** сохраняется запись с одновременно заданными повторами
  и длительностью
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Отсутствие длительности у упражнения на время

- **WHEN** сохраняется запись упражнения `measuredBy = TIME`
  без длительности
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Нулевая длительность отклоняется

- **WHEN** сохраняется запись упражнения `measuredBy = TIME`
  с длительностью = 0
- **THEN** операция завершается ошибкой
- **AND** запись не создаётся

#### Scenario: Повторяющиеся записи сохраняются отдельно

- **WHEN** сохраняются две записи с одним упражнением и одинаковыми
  параметрами (подходы, повторы/длительность, вес)
- **THEN** обе записи успешно сохраняются отдельными строками
  со своими идентификаторами
- **AND** обе отображаются в списке записей

### Requirement: Поддержка упражнений «на время»

Запись о выполнении SHALL поддерживать упражнения «на время»: повторы
не заданы, длительность в секундах задана. Длительность SHALL
сохранять переданное значение как есть (валидность ≥ 1 — см.
«Валидация полей записи»). Соответствие заполненных полей типу
упражнения SHALL обеспечиваться валидацией записи (см. «Валидация
полей записи»).

#### Scenario: Сохранение планки

- **WHEN** сохраняется запись «планка, 1 подход, 60 секунд»
  без повторов и веса
- **THEN** запись сохранена с длительностью = 60 и незаданными повторами

#### Scenario: Слой данных не навязывает соответствие

- **WHEN** сохраняется запись со ссылкой на упражнение
  `measuredBy = REPS`, у которой повторы не заданы, а длительность задана
- **THEN** операция завершается ошибкой: валидация записи требует
  повторы для `REPS` и длительность для `TIME`
- **AND** запись `measuredBy = TIME` содержит длительность,
  `measuredBy = REPS` — повторы; запись содержит только обязательное
  по `measuredBy` поле (повторы и длительность не задаются
  одновременно)
- **AND** хранение и чтение `measuredBy` — требование «Единый каталог
  для стандартных и пользовательских упражнений»
- **AND** запись не создаётся

### Requirement: Реактивный список записей

Слой данных SHALL предоставлять реактивный список всех записей о
выполнении (`Flow`), актуализирующийся при изменении таблицы записей.
Список SHALL быть упорядочен по дате/времени записи убыванием (новые
первыми).

#### Scenario: Состав элемента списка записей

- **WHEN** формируется элемент реактивного списка записей
- **THEN** он содержит идентификатор записи, название упражнения
  каталога (по ссылке `exerciseId`), номер иконки упражнения
  (`iconNumber` — подтягивается тем же JOIN на таблицу `exercises`),
  количество подходов, повторы (если заданы), длительность в секундах
  (если задана) и дату/время записи

#### Scenario: Пустое хранилище

- **WHEN** в хранилище нет записей
- **THEN** реактивный список эммитит пустой список

#### Scenario: Название упражнения в элементе списка

- **WHEN** запись ссылается на упражнение каталога
- **THEN** элемент списка содержит название этого упражнения

#### Scenario: Номер иконки в элементе списка

- **WHEN** запись ссылается на упражнение с назначенным `iconNumber`
  (например, подтягивания, 13)
- **THEN** элемент списка содержит этот `iconNumber`
- **AND** запись упражнения с `iconNumber = null` возвращает элемент
  с `iconNumber = null`

#### Scenario: Сортировка новых первыми

- **WHEN** в хранилище есть записи с разными датами
- **THEN** список упорядочен по дате/времени убыванием

#### Scenario: Список актуализируется при изменениях

- **WHEN** запись добавляется или удаляется
- **THEN** подписчик реактивного списка получает обновлённый список

### Requirement: Редактирование записи о выполнении

Существующая запись SHALL быть редактируемой: все поля записи могут быть
изменены. При редактировании время изменения SHALL обновляться,
время создания SHALL оставаться неизменным.

#### Scenario: Изменение подходов и повторов

- **WHEN** у существующей записи подходы меняются с 4 на 5,
  повторы — с 10 на 8
- **THEN** чтение возвращает новые значения
- **AND** время изменения больше прежнего, время создания не изменилось

### Requirement: Удаление записи о выполнении

Существующая запись о выполнении SHALL быть удаляемой. Удаление SHALL быть
безусловным: на запись нет внешних ссылок, она — лист дерева зависимостей.
Удаление SHALL возвращать `Result` с информацией об успехе или ошибке;
запись SHALL быть удалена из базы только при успешном результате.

#### Scenario: Удаление существующей записи

- **WHEN** вызывается удаление записи с идентификатором, существующим
  в таблице
- **THEN** операция завершается успехом
- **AND** запись отсутствует в базе при последующем чтении

#### Scenario: Удаление несуществующей записи

- **WHEN** вызывается удаление записи с идентификатором, отсутствующим
  в таблице
- **THEN** операция завершается успехом (отсутствие строки не является
  ошибкой — идемпотентность)

### Requirement: Удаление упражнения из каталога

Существующее упражнение каталога SHALL быть удаляемым при выполнении
обоих условий: упражнение создано пользователем (`isCustom = true`) и
на него не ссылается ни одна запись о выполнении. Удаление SHALL
возвращать `Result` с информацией об успехе или ошибке. Стандартное
упражнение и пользовательское со связанными записями SHALL быть
неудаляемыми. Удаление SHALL отклоняться типизированным исключением
(`LastActiveExerciseException`), если упражнение — единственное
активное в каталоге.

#### Scenario: Связанные записи блокируют удаление через NO ACTION

- **WHEN** удаляется пользовательское упражнение, на которое ссылается
  хотя бы одна запись
- **THEN** SQL-ограничение `NO ACTION` отклоняет удаление,
  репозиторий переводит ошибку в `Result.failure` с осмысленным
  сообщением о необходимости сначала удалить записи

#### Scenario: Удаление несуществующего id — ошибка, не идемпотентность

- **WHEN** запрашивается удаление упражнения с идентификатором,
  отсутствующим в каталоге
- **THEN** операция завершается ошибкой: запрашиваемой цели удаления
  не существует (в отличие от записи, где отсутствие строки
  идемпотентно)

#### Scenario: Порядок pre-check последнего активного

- **WHEN** выполняется удаление упражнения
- **THEN** проверка «последний активный» выполняется как pre-check
  после существующих проверок (несуществующий id, стандартное,
  связанные записи) и до `deleteById`

#### Scenario: Удаление несуществующего упражнения отклоняется

- **WHEN** вызывается удаление упражнения с идентификатором, отсутствующим
  в таблице `exercises`
- **THEN** операция завершается ошибкой
- **AND** каталог остаётся без изменений

#### Scenario: Удаление пользовательского упражнения без записей

- **WHEN** вызывается удаление пользовательского упражнения,
  на которое не ссылается ни одна запись
- **THEN** операция завершается успехом
- **AND** упражнение отсутствует в каталоге при последующем чтении

#### Scenario: Удаление стандартного упражнения отклоняется

- **WHEN** вызывается удаление стандартного упражнения
  (`isCustom = false`)
- **THEN** операция завершается ошибкой
- **AND** упражнение остаётся в каталоге

#### Scenario: Удаление пользовательского упражнения с записями отклоняется

- **WHEN** вызывается удаление пользовательского упражнения,
  на которое ссылается хотя бы одна запись
- **THEN** операция завершается ошибкой
- **AND** упражнение остаётся в каталоге
- **AND** все связанные записи остаются без изменений

#### Scenario: Удаление последнего активного упражнения отклоняется

- **WHEN** кастомное упражнение без записей — единственное активное
  в каталоге AND вызывается `deleteExercise(id)`
- **THEN** операция завершается
  `Result.failure(LastActiveExerciseException)`
- **AND** упражнение остаётся в каталоге

#### Scenario: Удаление архивного упражнения при последнем активном разрешено

- **WHEN** в каталоге ровно одно активное упражнение AND вызывается
  удаление архивного кастомного упражнения без записей
- **THEN** операция завершается успехом
- **AND** удаление архивного упражнения не ограничивается: экран
  архива продолжает удалять архивные упражнения независимо от
  количества активных
- **AND** архивное упражнение удалено, единственное активное остаётся

### Requirement: Массовый сброс данных

Приложение SHALL предоставлять операцию `deleteAllData`: удаление
всех записей о выполнении, всех упражнений каталога и всех категорий
одной транзакцией БД с последующим восстановлением стандартного
набора упражнений (`isCustom = false`) и стандартного набора из пяти
категорий (`PUSH`, `PULL`, `LEGS`, `CORE`, `CARDIO`). Настройки
приложения SHALL NOT затрагиваться.

#### Scenario: deleteAllData — единственное исключение из запретов

- **WHEN** выполняется `deleteAllData`
- **THEN** это единственная массовая операция, обходящая запреты
  индивидуального удаления стандартного упражнения (требование
  «Удаление упражнения из каталога») и стандартной категории (спека
  `category-data`), которые остаются запрещёнными
- **AND** операция запускается только с экрана «Данные приложения»
  после подтверждения пользователя

#### Scenario: Сброс очищает данные и восстанавливает стандартный набор

- **WHEN** `deleteAllData` завершился успешно
- **THEN** записи о выполнении отсутствуют
- **AND** кастомные упражнения отсутствуют
- **AND** стандартный набор упражнений присутствует (`isCustom = false`)
- **AND** кастомные категории отсутствуют
- **AND** стандартный набор из 5 категорий присутствует (`isCustom =
  false`, цвета из `StandardCategories` — значения зафиксированы по
  `Color.kt` на момент change)

#### Scenario: Сброс атомарен

- **WHEN** во время `deleteAllData` происходит ошибка БД
- **THEN** все данные SHALL остаться в состоянии до операции

### Requirement: Снимки каталога и записей

Репозиторий SHALL предоставлять разовые снимки данных: `getAllExercises`
— ВСЕ упражнения каталога (стандартные, кастомные, активные и
архивные — без фильтрации по `isArchived`), `getAllEntries` — все
записи о выполнении, `getAllCategories` — все категории (активные и
архивные). Снимки SHALL включать архивные объекты, чтобы при импорте
в новый экземпляр БД сохранялся весь набор.

#### Scenario: Назначение снимков

- **WHEN** `getAllExercises()` и `getAllCategories()` используются
- **THEN** это экспорт резервной копии (`app-data-management`) и
  дедупликация импорта
- **AND** восстановление архивного состояния пользователя — задача
  use-case импорта; репозиторий возвращает данные как есть

#### Scenario: Снимок возвращает полный каталог

- **WHEN** вызван `getAllExercises` при непустом каталоге
- **THEN** возвращены все упражнения — стандартные и кастомные

#### Scenario: Снимок включает архивные упражнения

- **WHEN** в каталоге есть и активные, и архивные упражнения
- **THEN** `getAllExercises()` возвращает и активные, и архивные
  в едином списке (с `isArchived` каждого упражнения)

#### Scenario: Снимок включает все категории

- **WHEN** в БД есть активные и архивные категории
- **THEN** `getAllCategories()` возвращает их в едином списке
  (с `colorArgb` и `isArchived` каждой категории)
- **AND** контракт — спека `category-data`, требование «Снимок всех
  категорий»

### Requirement: Массовый импорт данных

Репозиторий SHALL предоставлять транзакционную операцию
`importData(categories, exercises, entries)`: вставка только
переданных данных, разрешение имени упражнения в id внутри той же
транзакции; при любой ошибке — откат без частичных вставок.
Дедупликация и валидация выполняются выше репозитория (use-case);
репозиторий отвечает только за транзакционное хранение.

#### Scenario: Категории и упражнения вставляются в одной транзакции

- **WHEN** выполняется `importData(categories, exercises, entries)`
- **THEN** категории из файла вставляются в той же транзакции (с
  сохранением `colorArgb` и `isArchived` как в файле)
- **AND** упражнения ссылаются на категории по имени — как
  существующие в БД, так и вставленные из файла в этой же транзакции
- **AND** вставляемые из файла упражнения получают id от БД
  (`autoGenerate`), значение `isArchived` сохраняется как есть (если
  импортируется архивное — оно остаётся архивным в новом экземпляре
  БД)

#### Scenario: Импорт откатывается при сбое

- **WHEN** во время `importData` вставка завершается ошибкой
- **THEN** в БД нет изменений из этого импорта

#### Scenario: Импорт разрешает имена в id

- **WHEN** импортируемая запись ссылается на упражнение по имени
- **THEN** внутри транзакции запись связывается с id существующего либо
  вставленного упражнения

#### Scenario: Импорт сохраняет isArchived

- **WHEN** импортируется упражнение с `isArchived = true`
- **THEN** в БД упражнение сохраняется с `isArchived = true`
  (импорт архивного упражнения остаётся архивным)

#### Scenario: Упражнение ссылается на категорию из файла

- **WHEN** импортируемое упражнение ссылается на категорию, которой нет в БД,
  но она есть в переданном списке категорий
- **THEN** внутри транзакции категория вставляется, и упражнение ссылается
  на неё по имени

### Requirement: Архивация и восстановление упражнений каталога

Репозиторий SHALL предоставлять метод `setArchived(id: Long,
isArchived: Boolean): Result<Unit>` — единый метод для архивации
(`isArchived = true`) и восстановления (`isArchived = false`).
Метод SHALL обновлять существующее упражнение одним SQL-запросом
через `ExerciseDao.updateArchived(id, isArchived)` внутри
`runCatching`. Архивация SHALL отклоняться
(`LastActiveExerciseException`), если упражнение — единственное
активное в каталоге; восстановление SHALL NOT ограничиваться.

#### Scenario: Детали реализации setArchived

- **WHEN** `setArchived` выполняется
- **THEN** метод доступен и для стандартных, и для кастомных
  упражнений — архивация не зависит от `isCustom`
- **AND** реактивные подписки на `exercises()` и
  `archivedExercises()` обновляются без ручного refresh
- **AND** прочие ошибки БД возвращаются через generic
  `Result.failure`

#### Scenario: Guard последнего активного — детали

- **WHEN** выполняется проверка «последний активный» перед
  `updateArchived`
- **THEN** это count-запрос активных; guard закрывает race «сбор
  списка → подтверждение» (safety net), остаточный race «проверка →
  обновление» принимается (окно миллисекундное)
- **AND** стандартные упражнения считаются наравне с кастомными
- **AND** опустошение активного каталога делает создание упражнения и
  запись о выполнении невозможными

#### Scenario: Архивация активного упражнения

- **WHEN** вызывается `setArchived(7, true)` для активного упражнения
  с id = 7, когда в каталоге есть и другие активные упражнения
- **THEN** операция завершается успехом
- **AND** упражнение пропадает из `exercises()` (реактивный Flow
  эмитит новый список без него)
- **AND** упражнение появляется в `archivedExercises()`
- **AND** чтение `getExercise(7)` возвращает упражнение с
  `isArchived = true`

#### Scenario: Восстановление архивного упражнения

- **WHEN** вызывается `setArchived(7, false)` для архивного упражнения
  с id = 7
- **THEN** операция завершается успехом
- **AND** упражнение пропадает из `archivedExercises()`
- **AND** упражнение появляется в `exercises()` в позиции согласно
  текущей сортировке
- **AND** `getExercise(7)` возвращает упражнение с `isArchived = false`

#### Scenario: Архивация несуществующего упражнения отклоняется

- **WHEN** вызывается `setArchived(999, true)` для несуществующего id
- **THEN** операция завершается `Result.failure` с сообщением
  «Упражнение не найдено»
- **AND** несуществующий id возвращает
  `Result.failure(IllegalStateException("Упражнение не найдено"))`
- **AND** это race между сбором списка и подтверждением алерта (не
  идемпотентно, в отличие от удаления записи)
- **AND** каталог остаётся без изменений

#### Scenario: Архивация стандартного упражнения

- **WHEN** вызывается `setArchived(3, true)` для стандартного упражнения
  (`isCustom = false`) с id = 3, когда в каталоге есть и другие
  активные упражнения
- **THEN** операция завершается успехом (архивация разрешена и для
  стандартных)
- **AND** упражнение пропадает из `exercises()` и появляется в
  `archivedExercises()`

#### Scenario: Архивация последнего активного упражнения отклоняется

- **WHEN** упражнение с id = 7 — единственное активное в каталоге
  (остальные заархивированы или удалены) AND вызывается
  `setArchived(7, true)`
- **THEN** операция завершается
  `Result.failure(LastActiveExerciseException)`
- **AND** упражнение остаётся активным: `exercises()` по-прежнему
  содержит его, `archivedExercises()` — не содержит

#### Scenario: Восстановление последнего активного упражнения разрешено

- **WHEN** в каталоге ровно одно активное упражнение AND вызывается
  `setArchived(9, false)` для архивного упражнения с id = 9
- **THEN** операция завершается успехом — восстановление не
  ограничивается
- **AND** активных упражнений становится два

### Requirement: Реактивный список архивных упражнений

Репозиторий SHALL предоставлять `archivedExercises(): Flow<List<Exercise>>`
— реактивный список всех упражнений с `isArchived = true`. Сортировка —
та же, что у `exercises()`: `is_custom DESC, created_at DESC, name
COLLATE NOCASE` (контракт сортировки зафиксирован в
`exercises-screen/spec.md`, требование «Сортировка каталога —
кастомные сверху, новые первые»). При архивации/восстановлении
упражнения реактивный Flow SHALL эмитить обновлённый список без ручного
refresh.

#### Scenario: Архив пуст

- **WHEN** ни одно упражнение не заархивировано
- **THEN** `archivedExercises()` эмитит пустой список

#### Scenario: Архив содержит одно упражнение

- **WHEN** в БД есть одно заархивированное упражнение «Бег»
- **THEN** `archivedExercises()` эмитит список с этим упражнением

#### Scenario: Реактивность при архивации

- **WHEN** активное упражнение архивируется через `setArchived(id,
  true)`
- **THEN** подписчик `archivedExercises()` получает обновлённый
  список с добавленным упражнением

#### Scenario: Реактивность при восстановлении

- **WHEN** архивное упражнение восстанавливается через
  `setArchived(id, false)`
- **THEN** подписчик `archivedExercises()` получает обновлённый
  список без восстановленного упражнения

### Requirement: Реактивный счётчик архивных упражнений

Репозиторий SHALL предоставлять `archivedCount(): Flow<Int>` —
реактивный счётчик количества упражнений с `isArchived = true`.
Реализация — через `ExerciseDao.observeArchivedCount()` с
`@Query("SELECT COUNT(*) FROM exercises WHERE is_archived = 1")`.
При архивации/восстановлении упражнения Flow SHALL эмитить
обновлённое значение без ручного refresh. Используется UI для
условной видимости кнопки архива в `TopAppBar` экрана
`ExercisesScreen`.

#### Scenario: Архив пуст — счётчик 0

- **WHEN** ни одно упражнение не заархивировано
- **THEN** `archivedCount()` эмитит 0

#### Scenario: Архив не пуст — счётчик увеличивается реактивно

- **WHEN** в БД есть одно заархивированное упражнение AND
  пользователь архивирует ещё одно активное упражнение через
  `setArchived(id, true)`
- **THEN** `archivedCount()` эмитит 2 (обновлённое значение)

#### Scenario: Восстановление уменьшает счётчик

- **WHEN** в архиве 2 упражнения AND пользователь восстанавливает
  одно из них через `setArchived(id, false)`
- **THEN** `archivedCount()` эмитит 1

### Requirement: Опциональный номер иконки упражнения

Каждое упражнение каталога (стандартное и пользовательское) SHALL
иметь опциональный номер иконки `iconNumber`: `null` — иконка не
назначена, целое число — номер в стабильной таблице иконок (1..19,
номера не зависят от имён ресурсов). Значение SHALL сохраняться
вместе с упражнением и SHALL быть доступно при чтении каталога без
изменений. По умолчанию `iconNumber` SHALL быть `null` для новых
пользовательских упражнений.

#### Scenario: Хранение и валидация номера иконки

- **WHEN** определяется хранение `iconNumber`
- **THEN** в Room-сущности `ExerciseEntity` поле хранится как колонка
  `icon_number` типа `INTEGER` (nullable) без SQL DEFAULT
- **AND** номер иконки не валидируется по диапазону в слое данных:
  контроль соответствия ресурсам — ответственность UI-слоя, который
  рендерит иконку (неизвестный номер — тихий fallback «без иконки»)

#### Scenario: Сохранение и чтение номера иконки

- **WHEN** пользовательское упражнение сохраняется с `iconNumber = 5`
- **THEN** при чтении каталога упражнение возвращается с `iconNumber = 5`

#### Scenario: Упражнение без иконки

- **WHEN** пользовательское упражнение сохраняется без указания
  `iconNumber`
- **THEN** при чтении каталога упражнение возвращается с `iconNumber = null`
- **AND** номер назначается только при явном указании (UI выбора
  иконки — вне скопа)

#### Scenario: Стандартный набор prepopulate с номерами иконок

- **WHEN** база данных создаётся впервые и стандартный набор предзаполняется
- **THEN** все 13 стандартных упражнений имеют ненулевой `iconNumber`
  согласно фиксированному соответствию (номер — упражнение): 13 —
  подтягивания, 14 — австралийские подтягивания, 18 — приседания,
  15 — отжимания, 16 — отжимания с колен, 12 — выпады, 7 — брусья,
  15 — планка (осознанное переиспользование: отдельной иконки планки
  нет, планка попадает в группу push/core-статики), 8 — скручивания,
  1 — подъёмы ног в висе, 19 — приседания пистолетиком, 17 — бег,
  11 — скакалка

#### Scenario: Отсутствие иконки и её наличие различимы

- **WHEN** одно упражнение сохранено с `iconNumber = null`, другое —
  с `iconNumber = 0`
- **THEN** при чтении оба значения различимы: `null` и `0`

### Requirement: Мутации категорий в API репозитория — создание и обновление

Интерфейс `WorkoutDataRepository` SHALL предоставлять `addCategory(name:
String, colorArgb: Int): Result<Category>` и `updateCategory(id: Long,
newName: String, colorArgb: Int): Result<Unit>` (детали контрактов —
в сценариях ниже). Метод `renameCategory` SHALL быть удалён из кода
интерфейса `WorkoutDataRepository`: его поведение полностью покрывается
`updateCategory`.

#### Scenario: addCategory персистит переданный цвет

- **WHEN** вызывается `addCategory("Плечи", colorArgb)`
- **THEN** созданная категория имеет переданный `colorArgb`
- **AND** цвет приходит готовым из формы категории, без внутренней
  генерации (контракт — спека `category-data`, требование «Создание
  категории с цветом из формы»)
- **AND** репозиторий не генерирует цвет внутри операции

#### Scenario: updateCategory заменяет renameCategory

- **WHEN** экран категории сохраняет редактирование
- **THEN** вызывается `updateCategory(id, newName, colorArgb)` — одна
  транзакция обновляет имя и цвет, каскад ссылок упражнений по имени
  сохранён, стандартная категория отклоняется
  (`StandardCategoryDeletionException`)
- **AND** контракт — спека `category-data`, требование «Обновление
  категории — имя и цвет одной транзакцией»

### Requirement: Предзаполнение каталога и миграции схемы БД

При первом создании базы данных каталог упражнений SHALL содержать
ровно 13 стандартных упражнений с назначенными категориями (перечень —
в сценарии ниже). Каждое стандартное упражнение SHALL иметь тип
измерения `measuredBy`, и все они SHALL быть помечены как созданные
системой. Названия стандартных упражнений SHALL браться из
локализованных строковых ресурсов. Изменения схемы БД SHALL решаться
миграцией; деструктивный фоллбек SHALL NOT использоваться.

#### Scenario: Первый запуск приложения

- **WHEN** база данных создаётся впервые
- **THEN** каталог содержит ровно 13 упражнений, все помечены как стандартные
- **AND** состав с категориями: подтягивания (PULL), австралийские
  подтягивания (PULL), приседания (LEGS), отжимания (PUSH), отжимания
  на коленях (PUSH), выпады (LEGS), отжимания на брусьях (PUSH),
  планка (CORE), скручивания (CORE), подъёмы ног в висе (CORE),
  приседания пистолетиком (LEGS), бег (CARDIO), скакалка (CARDIO)
- **AND** пользовательских упражнений в каталоге нет

#### Scenario: Локализация при prepopulate

- **WHEN** prepopulate выполняется на устройстве с локалью `en`
- **THEN** названия стандартных упражнений записаны английскими строками
- **AND** при локали `ru` — русскими

#### Scenario: Разметка типов измерения при prepopulate

- **WHEN** база данных создаётся впервые
- **THEN** бег, планка и скакалка имеют `measuredBy = TIME`
- **AND** остальные десять стандартных упражнений имеют `measuredBy = REPS`

#### Scenario: Изменение схемы без миграции отклоняется

- **WHEN** приложение с новой версией схемы открывает базу, созданную
  предыдущей версией, и подходящая миграция не зарегистрирована
- **THEN** открытие базы завершается исключением (`IllegalStateException`)
- **AND** при расхождении версии файла БД с версией схемы и
  отсутствии зарегистрированной миграции (`addMigrations(...)`) Room
  бросает исключение при открытии базы; деструктивный фоллбек
  (`fallbackToDestructiveMigration`) не используется
- **AND** файл базы не пересоздаётся: `user_version` и существующие
  данные остаются в исходном состоянии
