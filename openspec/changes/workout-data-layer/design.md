## Context

Проект без БД и без слоя данных: UI (навигация, appearance) есть, хранение —
только DataStore настроек. DI — ручной, без Hilt; конвенции — в AGENTS.md
(`Result` с try/catch, без `!!`, StateFlow в VM). Модель уже спроектирована
в `docs/exercise-model-analysis.md` — этот документ фиксирует её как
решения и закрывает то, чего в черновике не было (состав категорий,
prepopulate-список, валидация, API репозитория).

## Goals / Non-Goals

**Goals:**

- Room-схема v1: таблицы `exercises` и `exercise_entries`, индексы, FK.
- Prepopulate 13 стандартных упражнений при первом создании БД.
- Репозиторий с API, достаточным для следующего change (экран
  создания/редактирования записи): каталог с поиском, CRUD упражнения,
  вставка/редактирование записи с валидацией.
- Schema export + тестовое покрытие (JVM + Room in-memory).

**Non-Goals:**

- UI: экран, ViewModel, интеграция FAB, список записей на главном экране —
  отдельный change. `MainActivity` не трогаем.
- Статистические запросы (агрегаты за периоды) — схема готова
  (индекс `date`, плоские поля), API не нужен.
- Таблица подходов (пирамиды) и таблица `workouts` — YAGNI (см. черновик).
- Удаление упражнений/записей — не запрошено, API не предоставляем.
- Иконки упражнений, `durationSec`-логика доступности поля — later.

## Decisions

### Decision 1: Room через KSP, не kapt

Kotlin 2.4.10 → kapt в maintenance-режиме, Room официально поддерживает
KSP2. Добавляем плагин `com.google.devtools.ksp` (версия, согласованная
с Kotlin 2.4.10) и `room-compiler` через `ksp(...)`. Room — последняя
стабильная 2.8.x. Альтернатива (SQLDelight) отклонена: Room — заявленный
стек проекта (AGENTS.md).

### Decision 2: Домен отделён от entity, категория — enum в домене

`ExerciseEntity` хранит `category: String`, доменный `Exercise` —
`category: ExerciseCategory`; маппинг — в репозитории.
Альтернатива (TypeConverter + типизированная entity) отклонена: entity
остаётся тупой структурой, enum не протекает в слой БД. Неизвестное
значение при чтении недостижимо штатно (пишет только наш репозиторий) —
fallback не вводим сознательно: если категория всё же испорчена (порча
БД, ручной дамп), маппинг падает громко — тихая подстановка «какой-нибудь»
категории хуже падения, испорченные данные должны быть видны сразу.
Контракт списка категорий фиксирует unit-тест полного набора.

### Decision 3: FK записи → упражнение с запретом висячих ссылок

`exercise_entries.exerciseId` — FK на `exercises.id` (NO ACTION —
SQLite отклонит вставку несуществующего упражнения). Индексы:
`exerciseId` (FK), `date` (будущие агрегаты за периоды). `workoutId`
— колонка есть, FK нет (таблицы `workouts` ещё нет — она появится своей
миграцией), в MVP всегда `null`. Альтернатива (CASCADE при будущем
удалении упражнения) — решение отложено до появления API удаления.

### Decision 4: Prepopulate через RoomDatabase.Callback + список из ресурсов

`RoomDatabase.Callback.onCreate` вставляет стандартные упражнения один раз
при создании файла БД (идемпотентность из коробки). Callback не имеет
доступа к `Context`, поэтому разрешение ресурсов происходит до него:
`standardExercises(context): List<StandardExercise>` собирает готовые пары
`(name: String, category)`, фабрика
`WorkoutDatabase.create(context, standardExercises)` замыкает этот список
в callback. Тип один — `StandardExercise(name, category)`, без внутреннего
«resolved»-варианта. Альтернативы: имя как `nameResId` внутри callback
(нечем разрешить — нет Context); хардкод русских строк — ломает
локализацию.

Состав prepopulate (13, без дублей):

| № | Упражнение | Категория |
|---|---|---|
| 1 | Подтягивания | PULL |
| 2 | Австралийские подтягивания | PULL |
| 3 | Приседания | LEGS |
| 4 | Отжимания | PUSH |
| 5 | Отжимания на коленях | PUSH |
| 6 | Выпады | LEGS |
| 7 | Отжимания на брусьях | PUSH |
| 8 | Планка | CORE |
| 9 | Скручивания | CORE |
| 10 | Подъёмы ног в висе | CORE |
| 11 | Приседания пистолетиком | LEGS |
| 12 | Бег | CARDIO |
| 13 | Скакалка | CARDIO |

### Decision 5: Репозиторий — concrete-класс, интерфейс позже

`RoomWorkoutDataRepository` в `data/repository/` — единственный слой
доступа к данным; в этом change у него нет потребителей (Decision 8),
поэтому интерфейс не вводим (AGENTS.md: «не плоди заранее»). Интерфейс
появится в следующем change вместе с первым ViewModel-тестом, которому
нужен fake-репозиторий на `MutableStateFlow` (конвенция `kotlin-testing`);
переезд concrete → interface + impl механический. API (списки — реактивные
`Flow`, точечные операции — `suspend` + `Result`):

```
fun exercises(query: String): Flow<List<Exercise>>
suspend fun addExercise(exercise: Exercise): Result<Long>   // только insert; для обновления — updateExercise
suspend fun updateExercise(exercise: Exercise): Result<Unit>
suspend fun addEntry(entry: ExerciseEntry): Result<Long>
suspend fun updateEntry(entry: ExerciseEntry): Result<Unit>   // ставит modifiedAt
suspend fun getEntry(id: Long): Result<ExerciseEntry?>
```

Сортировка/поиск — в SQL: `ORDER BY name COLLATE NOCASE`,
`WHERE name LIKE '%' || :query || '%' COLLATE NOCASE`. Альтернатива
(фильтрация в Kotlin) отклонена — SQL дешевле и индексируемо.
Спецсимволы LIKE (`%`, `_`) в пользовательском вводе сознательно не
экранируются — YAGNI для каталога из 13 названий; при заметном росте
каталога или поиске по комментариям добавить `ESCAPE '\'`.

### Decision 6: Валидация полей — одна точка, в репозитории

`addEntry`/`updateEntry` прогоняют запись через pure-функцию `EntryValidator`
(подходы ≥ 1; повторы — null или ≥ 1; вес — null или ≥ 0; workoutId — только
null: тренировки появятся отдельной миграцией, без неё колонка должна
оставаться пустой) и возвращают `Result.failure` без записи в БД. Валидатор
покрыт JVM-тестами. Существование упражнения валидатор не проверяет — за это
отвечает FK `exercise_entries.exercise_id → exercises.id` (`NO_ACTION`,
см. Decision 3): SQLite отклоняет insert с несуществующим `exerciseId`,
`runCatching` в репозитории превращает ошибку в `Result.failure`.
Альтернативы: CHECK-констрейнты в БД на поля (дублируют логику и хуже
диагностика) или валидация в UI (не защищает от будущих немодальных вызовов)
— отклонены.

### Decision 7: Schema export в `app/schemas/`

`ksp { arg("room.schemaLocation", ...) }` — JSON-схема v1 коммитится.
Стоит ноль усилий сейчас, без неё миграция v1→v2 (появление `workouts`)
не тестопригодна.

### Decision 8: Интеграция в app — отложена

БД и репозиторий создаются фабриками, но `MainActivity` в этом change
не меняется: живых вызовов из UI нет. Это осознанная поставка слоя
без потребителя — интеграция (1–2 строки в `MainActivity` + прокидывание
в `RootScreen`) входит в следующий change вместе с первым вызовом.
При интеграции создание БД — потокобезопасный синглтон
`getDatabase(context)` (`@Volatile` + `synchronized`): страховка от двух
экземпляров Room, когда появится второй потребитель (receiver/worker).

## Risks / Trade-offs

- **Названия стандартных упражнений фиксируются локалью первого запуска**
  → известный trade-off: смена локали устройства не переименует ранее
  созданные строки. Для MVP приемлемо; апгрейд-путь — хранить ключ ресурса
  вместо названия (миграция), если понадобится.
- **Версионная связка KSP ↔ Kotlin 2.4.10** → при добавлении плагина
  сверять совместимость; если стабильной пары нет — взять предыдущую
  стабильную Room.
- **Нет unique-констрейнта на название упражнения** → дубликаты названий
  допустимы в MVP (UI сможет подсветить при выборе). Ограничение добавится
  миграцией, если станет проблемой.
- **Поставка слоя без потребителя** → риск мёртвого кода до следующего
  change минимизирован DAO-тестами (единственный живой вызов — тесты);
  не растягивать разрыв: следующий change стартует сразу после этого.

## Migration Plan

Schema v1 — первая версия, миграций нет. Будущее: таблица `workouts`
с FK `workoutId` — отдельная миграция v1→v2, существующие строки не
трогаются (см. черновик модели). Rollback: изменение схемы до релиза —
просто удалить файл БД (dev-данные), после релиза — по правилам миграций
Room.
