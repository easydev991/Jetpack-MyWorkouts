# Design

## Context

См. proposal.md — Why. К моменту change уже существует: 19 пар
drawable-ресурсов (`res/drawable/<slug>.xml` + `<slug>_dark.xml`),
таблица `ExerciseIcons` (стабильные номера 1..19, `resolve(): Ref?`,
тихий fallback на `null`), колонка `exercises.icon_number` в schema v3,
поле `Exercise.iconNumber` в домене и бэкапе. `StandardExercise` уже
пробрасывает `iconNumber` в seed-SQL (значение `null`). Образец рендера —
`ExerciseIconsPreview.kt` (`isSystemInDarkTheme()` + `Image` без tint).

Пробелы: (1) `StandardExercises.kt` не назначает номера; (2) проекция
списка записей (`EntryListItemEntity` → `EntryListItem`) не содержит
`iconNumber`; (3) ни один экран иконку не рисует.

## Goals / Non-Goals

**Goals:**

- Показ иконки 24dp в трёх местах UI на единых правилах рендера.
- Назначение номеров иконок 13 стандартным упражнениям при prepopulate.
- Доставка `iconNumber` в строку записи главного экрана через существующий
  JOIN проекции.

**Non-Goals:**

- UI выбора/смены иконки при создании кастомного упражнения.
- Новые drawable-ассеты (набор 19 пар не расширяется).
- Анимации, бейджи, индикаторы.
- Локализация названий иконок (иконки — ресурсы без строк).
- Валидация `iconNumber` по диапазону в слое данных (не меняется,
  см. workout-data).

## Decisions

### Decision 1: Схема БД не меняется

Колонка `exercises.icon_number` уже в schema v3 (exercise-icon-mvp),
`version = 3` сохраняется, миграция и экспорт схемы не нужны.
Alternative: bump версии «на всякий случай» — отклонено: колонка
существует, менять схему не для чего.

### Decision 2: `EntryListItem.iconNumber: Int? = null` с дефолтом

Дефолт `null` повторяет патч `weightKg`/`comment`: ручные фикстуры
превью и JVM-тестов остаются компилируемыми, ревизуются только те, где
иконка нужна по смыслу. Alternative: обязательный параметр — отклонено:
ломает все фикстуры без поведенческой выгоды.

### Decision 3: Доставка иконки — расширение существующего JOIN

SELECT проекции списка записей дополняется `e.icon_number`, поле
добавляется в `EntryListItemEntity` и `Mappers.toListItem()`.
Alternative: отдельный запрос/подписка на каталог в ViewModel —
отклонено: название уже приходит тем же JOIN, второй источник данных
для одного поля — лишняя сложность.

### Decision 4: Единый internal-рендер `ExerciseIcon` в `ui/icons/`

Один маленький `@Composable internal fun ExerciseIcon(iconNumber: Int?,
modifier)` рядом с `ExerciseIcons`: внутри `resolve()` + выбор варианта
по `isSystemInDarkTheme()` + `Image(painterResource(...), 24.dp, без
tint, contentDescription = null)`; `resolve` вернул `null` — ничего не
рисует. Три экрана вызывают его, правила рендера не копируются.
Alternative: дублировать 5–6 строк в каждом экране — отклонено: три
копии одного условия разъедутся при первой правке. Новый публичный слой
не создаётся (AGENTS: реальные слои по мере фич). Четвёртый потребитель —
`ArchivedExercisesScreen`: он переиспользует `ExerciseListItemRow`
(контракт «Переиспользование ExerciseListItemRow» в
archived-exercises-screen), поэтому иконка попадает в строку архива
автоматически — поведение намеренное, отдельной правки не требует.

### Decision 5: Назначение номеров — таблица из proposal

В `StandardExercises.kt` каждому из 13 упражнений проставляется номер:
13/14/18/15/16/12/7/15/8/1/19/17/11 (полное соответствие — в delta-spec
workout-data). Планка → `PUSHUPS` (15) — осознанное переиспользование:
иконки plank нет, планка в группе push/core-статики; при появлении
иконки — пересмотреть. Иконки BARBELL, BARBELL_1..4, DUMBBELLS,
DUMBBELLS_1 остаются без стандартного упражнения — by design, для
будущих кастомных записей.

### Decision 6: Неизвестный номер — тихий fallback без изменений UI

Контракт `ExerciseIcons.resolve` (null/неизвестно → `null`) уже
зафиксирован; рендер просто не рисует. Никаких плейсхолдеров и логов на
каждой строке списка. Unknown-ветка эталонно проверяется UI-тестом на
главном экране (задача 4.2); экран упражнений и выпадающий список записи
получают ту же гарантию через общий `ExerciseIcon` — дублировать сценарий
и тест на каждом экране не нужно.

## Risks / Trade-offs

- [Расширение `EntryListItem` ломает ручные фикстуры] → дефолт
  `iconNumber = null` смягчает; фикстуры ревизуются точечно (превью и
  androidTest), компиляция укажет все места.
- [Планка с иконкой отжиманий семантически неидеальна] → помечено
  в proposal/design; пересмотр при появлении иконки plank — дёшево,
  это правка одной строки `StandardExercises.kt` (до релиза —
  деструктивная пересоздаст prepopulate).
- [7 drawable без потребителя] → by design (будущие кастомные записи),
  не bug; детектором мёртвых ресурсов не считаем.
- [Prepopulate-тесты] → `WorkoutDatabaseTest` обновляется: утверждение
  «все 13 с iconNumber = null» меняется на проверку назначенных номеров.
- [Правила рендера продублированы в трёх capability-спеках] → осознанно:
  спеки самодостаточны, кросс-ссылки между capability не поощряются;
  единая точка правды для кода — один `ExerciseIcon` (Decision 4), при
  изменении правил правка вносится во все три дельты синхронно.

## Migration Plan

Не требуется: схема не меняется; до первого релиза деструктивный
фоллбек пересоздаёт prepopulate с номерами у существующих установок.
