# Design

## Context

Экран обзора (`ui/screens/overview/`): три вкладки — StatsScreen,
RecordsScreen, ActivityScreen, общий `OverviewViewModel` + `OverviewUiState`
(`StatsUiState`/`RecordsUiState`/`ActivityUiState`). Записи с данными
упражнений приходят одним потоком `repository.entriesWithExercise()` в
`combine`; все расчёты — чистые функции в `domain/usecase/`
(`ComputeCategoryStats.kt` и соседи), пересчёт на каждую эмиссию. Донат
статистики считается по сумме подходов (`totalSets`, overview-stats-time-support
Decision 1) — и обзор, и drill-down. Прецедент «меньше двух — скрыть»:
таб-бар обзора скрывается при `visibleTabs.size < 2`. Мотивация — см.
proposal.md (Why).

## Goals / Non-Goals

**Goals:**

- Видимость сегментов пикеров Stats/Activity по дате самой ранней
  тренировки, реактивно на каждую эмиссию `entriesWithExercise()`.
- Clamp выбранного периода при исчезновении видимого.
- Проценты в легенде (категории и drill-down) вместо натуральных значений.
- Удаление ставшего мёртвым кода и ресурсов.

**Non-Goals:**

- Новые DAO-запросы и изменения схемы Room — самая ранняя дата считается
  из уже загруженного списка.
- Изменения RecordsScreen (его переключатель `PER_SET/PER_DAY` не трогаем).
- Изменение аналитических событий `SELECT_STATS_PERIOD` /
  `SELECT_ACTIVITY_PERIOD`.
- Изменение формата строк записей drill-down («3 х 12» / «3 х 30 сек.»).
- Сохранение видимых периодов в preferences — они вычисляются, не
  персистятся.

## Decisions

### D1. Чистые функции видимости рядом с типами периодов

`domain/usecase/` — например `visibleStatsPeriods(earliest: LocalDate?, today: LocalDate): List<StatsPeriod>` /
`visibleActivityPeriods(...)`: та же чистая модель, что и остальные расчёты
обзора (прецедент `ComputeCategoryStats`). Пороги — в днях от сегодня:
Stats — День всегда, Неделя `earliest < today`, Месяц `earliest <= today - 7`,
Год `earliest <= today - 30` (максимум); Activity — Месяц всегда,
Квартал `<= today - 30`, Полгода `<= today - 91`, Год `<= today - 182`
(окна 30/91/182/365 — каждый следующий период длиннее предыдущего).
Пороги намеренно ниже длин окон: «Квартал» виден уже при истории от 31 дня,
поэтому хитмап может быть частично пуст — ровная лестница периодов важнее
плотности сетки, это согласованное решение, а не недосмотр.
Канон значений порогов — дельта спеки (формальный источник); здесь —
обоснование выбора. Оборота канона «из четырёх сегментов» в дельте
сознательно нет: состав прежний, но видимых сегментов может быть
меньше четырёх — дельта описывает это отдельным предложением
про видимые периоды, не переименовывая сам пикер.
`today` — параметр функции, не `LocalDate.now()` внутри: тестируемость.
Вырожденный `earliest = null` (пустая БД — на экран не попасть, но защититься)
деградирует в «меньше двух сегментов» (только базовый период:
Stats — День, Activity — Месяц).
Альтернатива (отклонена): SQL-запрос MIN(date) в DAO — новая точка
реактивности и синхронизация с уже загруженным списком ради данных, которые
и так в памяти.

### D2. Самая ранняя дата и clamp — в существующем `combine` ViewModel

`OverviewViewModel` уже пересобирает `StatsUiState`/`ActivityUiState` на
каждую эмиссию: добавляем расчёт `earliest = entries.minOfOrNull { entryDay(it, zone) }`
(готовый хелпер `entryDay`, `ComputeCategoryStats.kt:76`, уже используется
в `ComputeHeatmapLevels`) и вызов чистых функций видимости в тот же
`combine` — без новых потоков;
единственный добавленный проход `minOf` по уже загруженному списку копеечен
на фоне существующих группировок (см. Risks).
Clamp: если `selectedPeriod !in visiblePeriods`, VM подменяет его последним
(самым длинным) видимым. Аналитика не стреляет на подмене — событие
`SELECT_*` отправляется только на явный пользовательский выбор.
Альтернатива (отклонена): хранить видимые периоды в UI-слое и фильтровать
в композабле — логика порогов ушла бы от JVM-тестов и дублировалась бы в
двух экранах.

### D3. Поля видимых периодов в UiState со значением по умолчанию «все периоды»

`StatsUiState.visiblePeriods: List<StatsPeriod> = StatsPeriod.entries` и
`ActivityUiState.visiblePeriods: List<ActivityPeriod> = ActivityPeriod.entries`:
существующие превью, демо-данные и тесты не меняются без причины; в
рантайме боевые значения приходят из VM.

### D4. Условный рендер — в местах вызова пикеров

StatsScreen: `if (visiblePeriods.size >= 2) StatsPeriodPicker(...)` — меньше
двух: пикер не показывается, донат поднимается на его место. ActivityScreen:
`SingleChoiceSegmentedButtonRow` при `>= 2`, иначе жирный заголовок месяцев
(`MonthsHeader`). Прецедент «меньше двух — скрыть» из таб-бара обзора.
Альтернатива (отклонена): прятать сегменты внутри самих компонент пикеров —
условие дублируется и компонент знает про бизнес-пороги.

### D5. Заголовок месяцев — standalone-названия по локали

Месяцы с данными внутри текущего (уже clamp'нутого) окна — источник —
уже загруженный `state.heatmap` (`count > 0`, уникальные `YearMonth`,
по возрастанию; считает композабл `MonthsHeader`, без нового поля
UiState): `DateTimeFormatter` со standalone-формой месяца ICU
(`L`-паттерн/`TextStyle.STANDALONE` по локали ru/en); первая буква
каждого названия — заглавная (касается только ru: standalone-форма en
и так с заглавной, ветка не нужна); названия месяцев локализует ICU,
код собирает заголовок, соединяя их разделителем « – ». Строковый ресурс — один, хранит только
разделитель (значение одинаково для ru/en, названия месяцев в ресурс
не входят).

### D6. Процент в легенде — расчёт в `ComputeCategoryStats`, вид по локали

Расчёт живёт в `ComputeCategoryStats` (рядом с тестами из tasks 3.1):
база процента — сумма `totalSets` отображаемых строк уровня. Баз
несколько: у уровня категорий — одна общая; в drill-down у каждой
категории — своя (равна сумме `totalSets` упражнений этой категории
из `exerciseTotals`). `totalSets` у
`CategoryTotal`/`ExerciseTotal` уже есть. Процент строки считается
в момент сборки от базы её уровня — без новых полей-сумм в
`CategoryStatsResult` — округлением `row.totalSets / база` до ближайшего
целого (`kotlin.math.roundToInt`); сумма может давать ≠ 100 % — это допустимо по спеке
и не «чинится». Базы ненулевые там, где строки показываются (прецедент —
фильтрация `totalSets > 0`); пустой период → подсказка, проценты не
рисуются. Один и тот же расчёт для уровней категорий и drill-down.
Процент полем не хранится — единственный носитель значения — готовая
строка `valueText`. Альтернатива (отклонена): считать процент прямо
в `legendItems()` — расчёт показательного значения ушёл бы из слоя
расчётов (JVM-тесты `ComputeCategoryStatsTest`, tasks 3.1) в UI-файл.
Форматирование — в `legendItems()` (сборка готовой строки `valueText`;
`LegendItemContent` остаётся тупым рендером): строковый ресурс
с плейсхолдером, вид по локали — ru «40 %», en «40%» (целое число);
парность ключей ru/en 1:1, тексты локале-специфичны. Форматирование
`DrillEntryRow` («3 х 12» / «3 х 30 сек.») не меняется.

### D7. Чистка мёртвого груза — одной задачей после перехода

После перевода легенды на проценты чистится мёртвый груз — полный
инвентарь и шаги канонично в tasks §6 (легендные функции
`DurationFormatter`, ресурсы длительностей/разделителя, поля
`totalReps`/`totalDurationSec` и хелперы в `ComputeCategoryStats`);
`overview_unit_reps` остаётся (RecordsScreen). Удалять одной группой задач
(§6) после обновления androidTest (§5): к этому моменту ни продакшн-код,
ни тесты на удаляемые символы не ссылаются, `make lint`/detekt между
задачами остаются зелёными, а compile-ошибки не размазываются по диффу.
То же касается перехода §3–§4 → §5: после 3.2 ассерты `overview_unit_reps`
в `StatsScreenTest` падают до 5.2, поэтому §3.2/§4 и §5.2–5.4 коммитятся
одним блоком (правило «make android-test перед коммитом задачи»).

## Risks / Trade-offs

- [Пересчёт видимых периодов на каждую эмиссию — лишний O(n) проход] →
  проход по уже загруженному списку в том же `combine`, где и так идут
  расчёты; `minOf` копеечен относительно существующих группировок.
- [Clamp «подменяет» выбор пользователя без его ведома] → подмена только
  когда выбранный период объективно недоступен (данных для него нет);
  аналитика пользовательского выбора не искажается.
- [Сумма процентов ≠ 100 % может смущать] → это следствие округления,
  задокументировано в спеке; альтернатива — largest remainder — усложнение
  без пользы для доната (доли видны графически).
- [Удаление ресурсов/функций ломает превью или тесты, не покрытые greps] →
  обновление androidTest и превью идёт раньше чистки (§5 → §6 в tasks),
  финальный полный прогон — в §7.

## Migration Plan

Без данных и API-миграций: Room-схема, preferences и бэкап не затрагиваются.
Откат — revert коммитов изменения.
