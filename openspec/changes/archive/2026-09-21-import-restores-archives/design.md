# Design

## Decision 1: Одностороннее правило архивации

Дедупликация применяет из файла только `isArchived = true` и только на
активное существующее упражнение. Симметричное «файл выигрывает»
отклонено: импорт устаревшего бэкапа в живой каталог молча
разархивировал бы решения, принятые после бэкапа. Цена одностороннего
правила — максимум «лишние строки в архиве», снимается вручную.

`iconNumber` по-прежнему не трогается: у чистой установки иконки уже
проставлены seeder'ом, а в старых бэкапах там `null` — перезапись
вернула бы прошлый баг.

## Decision 2: Применение через существующий `setArchived`, без изменения интерфейса

`mergeBackup` дополнительно возвращает id существующих упражнений,
которые нужно заархивировать (активные + в файле архив + имя совпало).
`invoke` после успешного `importData` применяет их через уже
существующий `repository.setArchived(id, true)` — интерфейс
`WorkoutDataRepository` и все его реализации не меняются. Сбой
отдельной архивации (практически недостижимый race: id взяты из
снимка, сделанного в том же вызове) проваливает импорт loud'ом —
повторный импорт безопасен: merge идемпотентен по построению.

Возвращаемый тип `mergeBackup` — `Triple` вместо `Pair` (internal,
новые JVM-тесты пишутся сразу под Triple).
