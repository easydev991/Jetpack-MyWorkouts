## Context

Слой данных и экран создания записи готовы: `ExerciseEntry.weightKg:
Double?` (`weight_kg` в `ExerciseEntryEntity`), различие `null`/`0.0`
закреплено тестами (`ExerciseEntryUpdateTest`, androidTest), `EntryCreateViewModel.
save()` сейчас пишет `weightKg = null`. Экран рендерит `EntryCreateUiState`
«глупо»; санитайзинг целочисленных полей (`sanitizeNumber`) и сброс
типозависимого поля живут в ViewModel. См. proposal.md — Why.

## Goals / Non-Goals

**Goals:**

- Видимость «Подходов» синхронизирована с типозависимым полем (после
  выбора упражнения).
- Опциональное поле «Доп. вес»: десятичный ввод, дефолт 0, сохранение
  в существующий `weightKg` без изменений слоя данных.
- Логика (санитайзинг, маппинг в `weightKg`) — чистые функции ViewModel,
  покрытые JVM-тестами (TDD).

**Non-Goals:**

- Ввод `0.0` как отдельного состояния из UI создания (см. Decision 1).
- Единицы измерения кроме кг, выбор веса из пресетов/истории.
- Сброс веса при смене упражнения (см. Decision 4).

## Decisions

### Decision 1: семантика `0` — `null` vs `0.0`

В домене `weightKg` различает `null` («собственный вес», без доп. веса)
и `0.0` («нулевой вес») — различие осознанное и покрыто тестами слоя
данных. Маппинг из UI создания: дефолт «0» и любой неспособный
распарситься в положительное число ввод (`""`, `"0"`, `"."`) → `null`
(«без доп. веса»); положительное значение → оно само. Явно введённый
«0» неотличим от нетронутого дефолта, поэтому тоже `null`. Состояние
`0.0` остаётся достижимым только для других продьюсеров (будущий режим
редактирования, импорт) — экран создания его не порождает.
Реализация: `weightText.toDoubleOrNull()?.takeIf { it > 0.0 }` в `save()`.

### Decision 2: санитайзинг десятичного ввода

`sanitizeWeight(input)` в ViewModel (рядом с `sanitizeNumber`, как
private-функция файла): оставить только цифры и десятичные разделители →
запятые нормализуются в точку (`toDoubleOrNull` не понимает `,`, а
русская Decimal-клавиатура даёт запятую) → не более одной точки (первая)
→ ведущие нули отбрасываются, но одиночный ноль перед точкой
сохраняется (`«012»` → `«12»`, `«000.5»` → `«0.5»`, `«0.»` → `«0.»`);
если после отбрасывания ничего не осталось — остаётся одиночный `«0»`
(`«0»` → `«0»`, `«00»` → `«0»` — иначе набор `«0.5»` посимвольно
очищал бы поле на первом тапе). Минус и прочие символы
отбрасываются — отрицательный вес невозможен. `«0.0»` проходит
санитайзер как текст, но парсится в `null` (Decision 1). `«5.»` и
`«5.0»` парсятся в `5.0` — это число, а не текст: вес в этом
изменении нигде не отображается, а показ целых весов без дробной
части («5 кг», не «5.0 кг») закреплён в Non-Goals proposal для
будущего изменения отображения; хвостовые точка/нули при вводе не
подрезаются — иначе нельзя набрать `«5.5»`/`«5.05»`. JVM-тест на
таблицу случаев.

### Decision 3: поле ввода — параметр у `NumberEntryField`

`NumberEntryField` получает `keyboardType: KeyboardType = KeyboardType.
Number`; поле веса вызывает его с `KeyboardType.Decimal`. Отдельный
`DecimalEntryField` отвергнут — это был бы дубль той же функции ради
одного параметра. Label — `entry_field_weight`: ru «Доп. вес (кг)» /
en "Extra weight (kg)": суффикс единицы в label — пользователь больше
нигде её не видит (спека: поле «в килограммах»); пометки «(обязательно)»
нет — поле опционально (её несут только обязательные поля).

### Decision 4: состояние и видимость

- `EntryCreateUiState.weightText: String = "0"`; `canSave` не меняется
  (поле опционально — proposal).
- `EntryCreateForm`: один общий блок `if (selectedExercise != null)` —
  «Подходы», `MeasuredByField`, поле веса (сразу после типозависимого);
  внутренняя ветка `null -> Unit` у `MeasuredByField` становится
  недостижимой из формы и остаётся как есть. Префилл «1» подходов
  сохраняется (появляются заполненными).
- Смена упражнения сбрасывает только типозависимое поле (как раньше);
  `weightText` сохраняется — вес не зависит от типа измерения, значение
  остаётся редактируемым.
- `EntryCreateScreenState` дополняется `onWeightChange: (String) -> Unit`
  (без дефолта, как у остальных колбэков — правятся все три места
  конструирования: экран, `previewScreenState` в превью, `stateFor` в
  androidTest); `EntryCreateViewModel.onWeightChange` — санитайзинг +
  сброс `isSaveError`, по образцу остальных полей.

## Risks / Trade-offs

- [Запятая/точка зависят от раскладки клавиатуры] → санитайзинг принимает
  оба разделителя и нормализует в точку (Decision 2) — JVM-тест фиксирует.
- [`0.0` недостижим из UI создания] → осознанно (Decision 1); различие
  `null`/`0.0` остаётся контрактным для слоя данных и режима
  редактирования.
- [Ввод вроде `«.»»` или `«0.»` неотличим от нуля] → `toDoubleOrNull`
  даёт `null`/`0.0` → сохраняется как «без доп. веса»; поле опционально,
  блокировать сохранение из-за него нельзя.
