# Design: fix-entry-list-live-update

## Context

Механика дефекта (анализ кода, см. proposal.md — Why):

- Композиционный корень ручного DI — `MainActivity.onCreate`: там создаются
  `AppSettingsDataStore`, `WorkoutDatabase.create(...)` и
  `RoomWorkoutDataRepository(...)`, затем передаются параметрами в
  `RootScreen` и фабрики ViewModel.
- `android:configChanges` в манифесте не задан → любое изменение
  конфигурации пересоздаёт Activity → создаётся второй инстанс БД.
- ViewModel'ы (scoped к backstack-записям NavController) переживают
  пересоздание и продолжают работать со старым инстансом БД; новые
  `EntryCreateViewModel`/`ExerciseCreateViewModel` создаются уже с новым.
- `InvalidationTracker` Room нотифицирует подписчиков только своего
  инстанса: записи через новый инстанс не переприквечивают Flow старого →
  `MainViewModel.uiState` замирает до конца процесса.
- Окно видимости: `SharingStarted.WhileSubscribed(5000)`. При возврате на
  экран позже 5 с Flow перезапускается свежим re-query и маскирует дефект;
  при возврате раньше 5 с — виден stale-список. Редактирование записи
  («открыл → сменил упражнение → сохранил») естественным образом укладывается
  в 5 секунд.

Реактивная цепочка в остальном корректна и не меняется: `observeEntries()`
(Room Flow с JOIN) → `RoomWorkoutDataRepository.entries()` →
`combine` в `MainViewModel` → `stateIn(WhileSubscribed(5000))`;
`remember(success.entries)` в UI закэширован правильным ключом;
`save()` пишет в БД до навигации назад.

## Goals / Non-Goals

**Goals:**

- Один инстанс `WorkoutDatabase`, `RoomWorkoutDataRepository` и
  `AppSettingsDataStore` на процесс приложения.
- Устранение целого класса дефектов «stale-список после пересоздания
  Activity» для всех экранов, не только главного.
- Детерминированные androidTest-репро всех трёх сценариев дельты,
  покрывающих оба пользовательских дефекта: два окна быстрого возврата
  (редактирование и создание записи) и пересоздание Activity.

**Non-Goals:**

- Введение DI-фреймворка (Hilt запрещён конвенциями проекта).
- Изменения слоя данных: DAO, репозиторий, схема БД, миграции — не
  трогаются.
- Пересмотр реактивной цепочки (`WhileSubscribed`, `combine`) — она
  корректна.
- `android:configChanges` в манифесте как «фикс» — явно отвергнут
  (см. Decisions).

## Decisions

### Decision 1: Композиционный корень — `MyWorkoutsApplication`

Создаётся `MyWorkoutsApplication` с `lazy`-свойствами `dataStore`,
`database`, `repository`; в манифесте регистрируется
`android:name=".MyWorkoutsApplication"`. `MainActivity` берёт зависимости
из `(application as MyWorkoutsApplication)` и больше ничего не создаёт.

- Почему Application, а не singleton-объект: Application — стандартная
  точка процесс-скоупа Android; ленивая инициализация сохраняет текущее
  время старта; структура проекта (AGENTS.md) уже отводит место под
  `MyWorkoutsApplication.kt` и будущий `di/`.
- Альтернатива 1 — `android:configChanges="..."` в манифесте: не покрывает
  все триггеры пересоздания (локаль, размер экрана/фолд, uimode из
  системы, изменения от производителя), считается антипаттерном; отклонено.
- Альтернатива 2 — `onRetainCustomNonConfigurationInstance`: спасает только
  часть пересозданий, усложняет корень; отклонено.
- Альтернатива 3 — Hilt/Koin: против конвенций проекта (manual DI);
  отклонено.

`AppSettingsDataStore` переносится вместе с БД: пересоздание DataStore на
том же файле при пересоздании Activity — риск того же класса
(несколько активных инстансов на один файл).

### Decision 2: Репро-тесты — интеграционные, на реальном приложении

Новый androidTest-класс по образцу `ExerciseCreateLiveUpdateIntegrationTest`
(`createAndroidComposeRule<MainActivity>`, файловая БД приложения):

- Сценарий A (быстрый возврат): вставить запись напрямую в БД → открыть
  её редактирование из контекстного меню → сменить упражнение → сохранить →
  НЕ ждать таймаут подписки → на главном экране строка показывает новое
  название. Ключевое отличие от существующего теста каталога: без паузы
  5.3 с — именно быстрый возврат является окном дефекта.
- Сценарий B (пересоздание Activity): аналогично, но между подготовкой
  данных и правкой выполняется `scenario.recreate()` — детерминированный
  триггер пересоздания вместо поворота.
- Сценарий C (создание при быстром возврате): вставить упражнение напрямую
  в БД → создать запись через UI с этим упражнением → сохранить → НЕ ждать
  таймаут подписки → новая запись отображается в списке. Второе окно <5 с:
  A покрывает stale-имя (дефект 1), C — пропавшую запись (дефект 2).
- Уникальные имена упражнений на прогон (`System.currentTimeMillis`),
  как в существующем тесте: данные файловой БД переживают прогоны.
- Порядок работ — TDD по правилам проекта: тесты сначала падают
  (сценарий B — гарантированно, сценарий A — при наличии пересоздания в
  истории процесса), затем фикс делает их зелёными.

Почему не JVM-тест: дефект живёт на стыке жизненного цикла Activity и
инстансов БД — в JVM изоляции (`FakeRepository` на `MutableStateFlow`)
невоспроизводим по построению.

### Decision 3: Диагностика, если репро не воспроизведётся

Если сценарий A зелёный до фикса (пересоздания в прогоне не случилось) —
это ожидаемо: A проверяет окно <5 с на текущем процессе, B — сам триггер.
B остаётся главным детерминированным репро. Инвариант «один инстанс БД
на процесс» дёшево проверять на каждом прогоне: временный лог
`identityHashCode(database)` в точке создания БД (до фикса — в
`MainActivity.onCreate`), прогон сценария B и `logcat` — больше одного
создания на процесс без холодного старта = подтверждение механики
(безусловный шаг — tasks 2.3).

## Risks / Trade-offs

- [AndroidTest'и пишут в файловую БД приложения (прецедент —
  `ExerciseCreateLiveUpdateIntegrationTest`)] → уникальные имена на прогон;
  тесты не удаляют чужие данные; для полной изоляции можно предварительно
  вызвать `deleteAllData` через репозиторий приложения.
- [Flaky на быстрых/медленных машинах: окно <5 с зависит от скорости
  UI-действий] → `waitForIdle` между шагами; сценарий B не зависит от
  таймингов вообще (recreate — явный триггер) и является основным
  регрессионным guard'ом.
- [Application-скоуп продлевает жизнь БД на весь процесс] → это и есть
  цель; при необходимости ресурсы освобождаются `close()` (для одного
  процесса не требуется).
- [Фикс меняет точку создания зависимостей — риск пропустить usage в
  тестах] → `MainActivity` остаётся единственным потребителем
  Application-каста; существующие androidTest'ы создают собственные
  инстансы БД и не зависят от корня.

## Migration Plan

Миграция данных не требуется: имя файла БД, схема и prepopulate не
меняются. Откат — revert коммита: изменения локальны (новый класс,
манифест, `MainActivity`, тесты).

## Open Questions

Нет — подход и границы зафиксированы; уточнение «падает ли сценарий A до
фикса» не влияет на спеку и разбивку задач (Decision 3).
