## Context

Резервная копия собирается в `ExportBackupUseCase.buildBackupJson` (чистая
функция рядом с use-case) и разбирается в `ImportBackupUseCase.parseExercise`
(тоже чистая). Доменная модель `Exercise` уже имеет `isArchived: Boolean`
с дефолтом `false`, Room-сущность хранит колонку `is_archived` (v3 БД),
репозиторий умеет фильтровать каталог по этому полю — слой данных готов.
Пробел — сериализация/десериализация и спека `app-data-management`. См.
`proposal.md` (Why) и `specs/app-data-management/spec.md` (MODIFIED
Requirements).

## Goals / Non-Goals

**Goals:**
- Поле `isArchived` пишется в JSON всегда (для активных и архивных
  одинаково).
- При импорте `isArchived` читается из файла и проставляется
  восстановленному упражнению (в т.ч. `true` → попадание в архив).
- Старые v1-файлы без `isArchived` остаются валидными: дефолт `false`.
- Версия формата остаётся `1` (по прецеденту `iconNumber`).

**Non-Goals:**
- Бамп `version` до `2`, отдельные парсеры для разных версий.
- Изменение существующего требования «файл недоверенный → `isCustom = true`»
  для вставленных упражнений: `isArchived` доверяем (это пользовательские
  данные, не схема БД).
- Изменение поведения архивации/восстановления на экране упражнений.

## Decisions

### 1. Дефолт `isArchived = false` на чтении для обратной совместимости

Используем `obj.optionalBoolean("isArchived") ?: false` (хелпер
`optionalBoolean` описан в Decision 2). Старые v1-файлы (без поля)
дают `null` от хелпера → дефолт `false`. Неправильный тип значения
(строка `"true"`, число `0/1`) даёт `invalidFile(...)` — так же, как
для `comment`, `iconNumber` и т.д.; файл отклоняется как несовместимый.
Рассматривал `requiredBoolean` с миграцией версии — отвергнуто: та же
стратегия миграции, что у `iconNumber` (см. archive
`2026-09-15-exercise-icon-mvp`) — без бампа `version`. Дефолт у
`isArchived` отличается от `iconNumber` (Boolean → `false`, не `Int?` →
`null`): доменная модель хранит `isArchived` как non-nullable `Boolean`,
поэтому отсутствующее поле мапится в `false`, а не в `null`.

### 2. `iconNumber`-style парсер: `optionalBoolean` хелпер рядом с `optionalInt`

Сейчас в `ImportBackupUseCase` уже есть `optionalString`, `optionalInt`,
`optionalDouble` (line 302-321). Добавляем `optionalBoolean` тем же
образом — маленькая чистая функция, симметрично существующим хелперам:
`null`/`JSONObject.NULL` → `null`, `Boolean` → значение, остальные типы
→ `invalidFile(...)`. Альтернатива — `obj.opt("isArchived") as? Boolean
?: false` inline — отвергнуто: смешивает два стиля чтения полей в одной
функции `parseExercise`, где все остальные поля читаются через хелперы.

### 3. Поле пишется всегда (а не только для архивных)

В `buildBackupJson` для каждого упражнения безусловно
`.put("isArchived", exercise.isArchived)`. Альтернатива —
писать только `true`, а отсутствие трактовать как `false` — отвергнуто:
теряется единообразие с `iconNumber` (тоже всегда пишется) и ломается
симметрия «JSON ↔ БД». Семантика `(опционально)` в спеке для
`isArchived` не применяется — это не nullable-поле.

### 4. `isCustom` остаётся доверенным правилом «файл недоверенный»

Сейчас в `mergeBackup` вставленные упражнения принудительно получают
`isCustom = true` (use-case ImportBackupUseCase.kt:142 — `it.copy(isCustom = true, id = 0L)`).
`isArchived` этим не трогаем: пользовательский архивный статус — это
пользовательские данные, а не признак каноничности в стандартном наборе.
Правило для `isCustom` оставлено как есть.

## Risks / Trade-offs

- **Пользовательские упражнения-импортанты, помеченные в файле как
  `isArchived = true`, но не имеющие `isCustom = true`** — после merge
  получат `isCustom = true` (по Decision 4) и `isArchived = true`. Это
  новое сочетание: архивное пользовательское упражнение, помеченное как
  кастомное. Удаление через экран редактирования будет доступно (потому
  что `isCustom = true`). Принимаемо: импорт только добавляет, ничего
  не перезаписывает; пользователь сам решает, оставить или восстановить
  из архива.

- **Дедупликация не трогает существующий архивный статус** — если у
  пользователя упражнение «X» сейчас активно, а в файле оно архивное,
  после восстановления файл-архивность проигнорируется, активное
  останется активным. Решение осознанное: merge только добавляет,
  правило «существующее не изменяется» уже зафиксировано для
  `iconNumber`, переносим его и на `isArchived`.

- **Старый бэкап без `isArchived`** теперь при импорте выглядит для
  пользователя как «все восстановленные упражнения активны» — даже те,
  что в оригинале были архивными. Это собственно исходный баг, который
  фикс закрывает только для бэкапов, сделанных обновлённой версией.
  Исторические архивы восстановлению архивности не подлежат
  (принципиально — `isArchived` в них не сохранён).

## Migration Plan

Миграция не требуется: Room-колонка `is_archived` уже существует (v3
БД), поле в доменной модели уже есть. Изменения — только в двух
функциях use-case'ов и в спеке. Откат — revert двух файлов, данные
никак не затронуты (поля в JSON игнорируются старой версией).
