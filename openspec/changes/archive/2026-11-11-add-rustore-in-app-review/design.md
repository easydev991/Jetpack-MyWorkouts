# Design

## Context

Кнопка «Оценить приложение» есть только в rustore flavor (компайл-тайм-гейт `BuildConfig.RUSTORE_FEATURES` в `MoreScreen`, спека `more-screen`) и открывает `ACTION_VIEW` на страницу отзывов `https://apps.rustore.ru/app/com.myworkouts/reviews`. Flavor-дифференциация в проекте — только BuildConfig-флаги внутри `main`: flavor source-sets и flavor-зависимостей нет. DI — ручной, без модуля зависимостей: композиционный корень `MyWorkoutsApplication` (process-singleton'ы `AppSettingsDataStore`, `WorkoutDatabase`, `RoomWorkoutDataRepository`), `MainActivity` получает их через `application as MyWorkoutsApplication`, фабрики ViewModel собираются в `RootScreen.kt` (`AppNavHost` + `NavDestinations.kt`). Записи создаются с экрана записи (`Screen.EntryCreate`, FAB главного экрана): `EntryCreateViewModel.save()` после успешного `repository.addEntry` вызывает `onSaved()` — навигацию назад на главный экран. Хранилище настроек — `AppSettingsDataStore` (preferences DataStore, suspend-сеттеры + Flow, тесты через `PreferenceDataStoreFactory`); аналитика — sealed interface `AnalyticsEvent` с ровно тремя типами (`ScreenView`/`UserAction`/`AppError`) поверх `AnalyticsProvider` (Noop в debug, Firebase в release); домен защищён guard-тестом `DomainPurityTest`. Сборка: minSdk 26, AGP 9.5.1, Kotlin 2.4.21, release с R8 (`isMinifyEnabled = true`); `settings.gradle.kts` — `FAIL_ON_PROJECT_REPOS`. Автоматических запросов оценки нет. Мотивация — proposal.md; требования — specs/app-review/spec.md. Эталон реализации — change `2026-11-09-add-rustore-in-app-review` проекта JetpackDays (коммит 3fff023c): SDK-флоу, иерархия ошибок и эмпирика ручной проверки перенесены оттуда.

Ключевое ограничение SDK: публичного API предпроверки установки RuStore нет — установка проверяется внутри SDK, результат только через `onFailure` (`RuStoreNotInstalledException` из иерархии `RuStoreException`). SDK-флоу двухфазный: `requestReviewFlow()` → `ReviewInfo` (~5 минут жизни) → `launchReviewFlow(reviewInfo)`; дневной лимит отображений регулируется на стороне RuStore (тихий `RequestLimitReached`).

## Goals / Non-Goals

**Goals:**

- Изолировать SDK целиком в flavor-артефактах: github-сборка компилируется и работает без SDK-зависимости.
- Сохранить чистоту домена: контракт лаунчера и milestone-логика — без android-типов, проходят `DomainPurityTest`.
- Переиспользовать проектные паттерны: manual DI через композиционный корень, preferences DataStore, sealed-события аналитики, TDD на доменную логику.
- Не трогать существующие спеки (`more-screen`, `app-data-management`, `workout-entry-screen`): новая capability `app-review` — единственная дельта.

**Non-Goals:**

- Не менять функциональность github flavor — поведение не меняется вообще, SDK не подключается.
- Не менять кнопку «Оценить приложение» — отображение и поведение как сейчас (`ACTION_VIEW` на страницу отзывов); SDK-флоу кнопкой не инициируется (решение владельца; соответствует рекомендации доков SDK не использовать кнопку как триггер).
- Не подключать BOM RuStore и другие SDK RuStore (billing/push) — только review.
- Не строить собственные UI-диалоги оценки и не задавать пользователю вопросов до/во время SDK-флоу (прямо запрещено правилами SDK).
- Не отслеживать «пользователь уже оценил» своими механизмами — только через ошибки SDK.
- Не учитывать записи, созданные импортом бэкапа, в счётчике триггеров.
- Не повышать лимит Detekt и не вводить исключения из офлайн-правила в коде.

## Decisions

### D1. Первые flavor source-sets вместо расширения BuildConfig-паттерна

Код, импортирующий классы SDK, физически не может лежать в `main`: с зависимостью `rustoreImplementation` github-сборка сломается на компиляции. Поэтому вводятся `app/src/rustore/` и `app/src/github/` — первые flavor source-sets в проекте.

- В каждом source-set — своя реализация контракта лаунчера и своя фабрика с одинаковым публичным FQN (`com.myworkouts.review.ReviewFlowLauncherFactory`): `main` ссылается на фабрику один раз (точка — `MyWorkoutsApplication`, см. D6), конкретная реализация подставляется на этапе компиляции flavor'а (стандартный flavor-паттерн), выбор не идёт через `if (RUSTORE_FEATURES)` в рантайме.
- Альтернативы: reflection-загрузка SDK-класса из `main` (отклонено — хрупко, ломает R8-предсказуемость); `compileOnly` + рантайм-проверки (отклонено — не убирает классы из github-APK без дополнительной настройки); отдельный Gradle-модуль (отклонено — избыточно для одной интеграции).

### D2. Домен: чистый контракт + чистая milestone-логика

- Контракт лаунчера review-флоу — порт в домене, без android-типов (прецедент порта — `domain/crash/CrashReporter`): новый пакет `domain/review/` — интерфейс `ReviewFlowLauncher` (`suspend fun launch(): ReviewFlowOutcome`), sealed interface `ReviewFlowOutcome` (`data object Shown` / `data class Error(val errorType: ReviewErrorType)`, стиль sealed-иерархий по AGENTS.md) и enum `ReviewErrorType` — доменная классификация ошибок (`NOT_INSTALLED`, `OUTDATED`, `USER_UNAUTHORIZED`, `REQUEST_LIMIT_REACHED`, `REVIEW_EXISTS`, `UNKNOWN`); значения enum — wire-значения аналитики. Реализация в rustore source-set оборачивает `RuStoreReviewManagerFactory.create(context)` и двухфазный флоу, маппит иерархию `RuStoreException` в эту модель (см. D5). Альтернатива: интерфейс в `data/` (отклонено — домен не должен зависеть от `data`, и use-слою нужен тип без android-зависимостей для тестов).
- Классификация сознательно не шире шести значений (решение по эталону): иерархия `RuStoreException` SDK содержит и другие подтипы — бан-ветки `RuStoreApplicationBannedException`/`RuStoreUserBannedException`, `RuStoreInvalidReviewInfo` (по докам SDK), но в `ReviewErrorType` они не добавляются: это расширило бы wire-контракт аналитики `error_type`, а бан-ветки в реальном флоу до публикации сборки и первого отзыва недостижимы. Всё неименованное уходит в `UNKNOWN` правилом базовой ошибки (маппинг — 4.1); уточнение классификации после публикации — решение владельца (см. tasks 8.4).
- Milestone-логика (пороги `[1, 5, 15]`, «наивысший достигнутый непройденный», лимит сессии, «pending не перезаписывается») — чистый use case `ReviewMilestoneDecider` в `domain/usecase/`: вход — состояние счётчиков (`ReviewCounters` из `domain/model/`: `createdEntriesCount`, `passedMilestones`, `pendingMilestone`) и флаг «авто-запрос уже выполнялся в этой сессии», выход — решение (`sealed interface ReviewMilestoneDecision`: `data class Plan(val milestone: Int)` / `data object None`). Пороги — константа use case. Тестируется на JVM без Android.
- Флаг «авто-запрос уже выполнялся в этой сессии» (требование лимита сессии из спеки) — in-memory состояние presentation-слоя, не персистится и в хранилище из D3 не входит. Держатель — `ReviewSessionHolder`, общий in-memory singleton (flavor-независимый, в `main`): пишет `MainViewModel` при запуске авто-флоу, читает `EntryCreateViewModel` при планировании milestone — оба ViewModel получают один и тот же экземпляр через фабрики (D6).
- Непоказанный pending не перезаписывается: пока pending существует, достижение более высокого milestone даёт решение «не запрашивать», промежуточный milestone остаётся непройденным и подхватывается при следующем создании записи после показа текущего pending. Фактический порядок порогов может отличаться от 1→5→15: при pending=1 и скачке счётчика сразу к 15 порядок будет 1→15→5 (правило «наивысший достигнутый непройденный» выбирает 15, 5 подхватывается позже), но ни один порог не «проглатывается» — все milestones в итоге выполняются, требование спеки сохраняется (решение владельца: pending не перезаписывается, пока не показан). Правило «пока pending существует» означает непоказанный pending: жизненный цикл pending завершается запуском SDK-флоу на главном экране — milestone помечается пройденным, а совпадающий pending снимается атомарно (D3/D5), после чего следующее создание записи планирует следующий milestone.
- Проверка установки RuStore приложением не выполняется ни в каком виде: отсутствие RuStore проявляется как ошибка SDK-флоу (`RuStoreNotInstalledException`), которая в авто-режиме обрабатывается тихо (спека «Тихая обработка ошибок авто-запроса»). `<queries>` в манифесте приложения не нужен: SDK 10.5.2 сам декларирует видимость пакета RuStore intent-based (`<queries><intent><action android:name="ru.vk.store.provider.review.RemoteReviewFlowProvider"/></intent></queries>`) в манифесте библиотеки — декларация мержится автоматически (manifest merger; подтверждено распаковкой AAR в эталоне).
- Альтернатива: вся логика в UI-слое (как в `rateApp` кнопки) — отклонено: нет тестируемости и нарушает сложившуюся структуру.

### D3. Отдельное хранилище счётчиков

Новый preferences DataStore `ReviewCountersDataStore` (`data/preferences/`, по образцу `AppSettingsDataStore`: конструктор с `DataStore<Preferences>`, `Companion.create(context)` с делегатом `preferencesDataStore`, unit-тесты через `PreferenceDataStoreFactory.create`) на отдельном файле `review_counters`: счётчик созданных записей (int), пройденные milestones (строковый набор — int-набор сериализуется строкой, по аналогии с существующей обработкой enum-ключей), pending-milestone (int, отсутствие — sentinel). API: реактивный `Flow<ReviewCounters>` + suspend-операции (атомарный инкремент внутри `edit {}`, установка/сброс pending, полный `reset()`, отметка milestone пройденным — одним атомарным `edit {}` добавляет milestone в пройденные и снимает совпадающий pending).

- Альтернатива: расширить `AppSettingsDataStore` новыми ключами — отклонено: смешивает пользовательские настройки UI со служебными счётчиками и усложняет точечный сброс (в KDoc `AppSettingsDataStore` прямо сказано: новые ключи — точечно по фичам).
- Сброс вызывается из флоу полного удаления данных — `AppDataViewModel.deleteAllData()` в ветке `onSuccess` (`AppDataResult.DELETED`), там же, где удаляются записи; при провале удаления счётчики не трогаются. Флаг сессии (`ReviewSessionHolder`, D2) при сбросе не трогается: авто-запрос после «Удалить все данные» подчиняется лимиту сессии — если авто-запрос в этой сессии уже выполнялся, он откладывается до следующего создания записи в новой сессии приложения. Файл `review_counters.preferences_pb` живёт в app-хранилище — `pm clear`/удаление приложения тоже сбрасывают (справочно для ручной проверки).
- Инвариант «pending не входит в `passedMilestones`» гарантируется без отдельной guard-ветки в use case (ответ на ревью, по эталону): decider планирует только milestone вне passed и только при отсутствии pending (D2), а отметка пройденным снимает совпадающий pending атомарно — состояние «pending ∈ passed» возникнуть и сохраниться не может. Чтение счётчиков может упасть `IOException` (сбой файла DataStore) — потребители обрабатывают тихо (D5).

### D4. Без предпроверки установки RuStore и без собственного `<queries>`

Приложение не проверяет установку RuStore самостоятельно: кнопка «Оценить приложение» SDK не вызывает (поведение без изменений), а авто-флоу узнаёт об отсутствии RuStore через ошибку подготовки данных (`RuStoreNotInstalledException`) и обрабатывает её тихо. Подробности и обоснование — D2.

### D5. Точки интеграции в UI

- **Хук счётчика** — `EntryCreateViewModel.save()`, ветка создания (`originalEntry == null`). Точка хука — после успешного `repository.addEntry`, внутри ветки успеха (`onSuccess`) непосредственно перед `onSaved()`: `onSaved()` закрывает экран (навигация назад на главный экран), поэтому планирование milestone выполняется в той же корутине до `onSaved()` — pending гарантированно установлен к моменту возврата на список. Успешным созданием для счётчика считается сохранение, дошедшее до `onSaved()`; ветка редактирования (`repository.updateEntry`) счётчик не трогает; импорт бэкапа (`ImportBackupUseCase` в `AppDataViewModel`) хук не проходит. Гейт — флаг `isReviewEnabled: Boolean`, инъекция через фабрику ViewModel (`RootScreen.kt`, вызов `EntryCreateViewModel.factory(...)` передаёт `BuildConfig.RUSTORE_FEATURES`): на github-сборке счётчик не ведётся вовсе — согласуется со строгой формулировкой спеки «авто-запросы MUST NOT инициироваться ни при каких условиях»; unit-тесты в общем `app/src/test/` передают флаг явно (true/false), рантайм-гейт их не ломает. Отдельного доменного use case создания записи в проекте нет (сохранение идёт через репозиторий из ViewModel), и заводить его только ради счётчика — лишний слой; хук — в presentation-слое, логика решения — в домене (D2). Оркестрация хука: `if (isReviewEnabled && original == null)` → инкремент счётчика → чтение `ReviewCounters` → `ReviewMilestoneDecider.decide(...)` с флагом из `ReviewSessionHolder` → при `Plan(n)` установка pending.
- **Показ pending** — главный экран (`MainViewModel` + `MainScreen`). Скоуп запуска — `viewModelScope` (решение по эталону: ViewModel скоуплена к start destination и переживает навигацию, запуск не привязан к композиции; уход с экрана в окне задержки показ НЕ отменяет — SDK-форма системная, закрывается BACK; отмена по уходу — сознательный отказ эталона, UX-трейдофф). Две точки запуска одного метода `onMainScreenShown()` (по эталону): (1) `init` ViewModel — персистентный pending на старте сессии; (2) `LaunchedEffect(Unit)` в `MainScreen` при каждом входе на экран — pending, запланированный в той же сессии (ViewModel переживает навигацию, init повторно не выполнится; NavHost не хранит композицию ушедших destination — эффект перезапускается при каждом возврате). Повторные запуски сериализуются мьютексом внутри ViewModel: обе точки могли пройти проверку holder'а до отметки флага — иначе двойной запуск флоу. Последовательность метода: гейт `isReviewEnabled` (инъекция в `MainViewModel.factory` из `NavDestinations.kt`) + github-лаунчер no-op → чтение pending из `ReviewCountersDataStore` (сбой `IOException` файла счётчиков — тихий лог и выход, повтор при следующем возврате на экран) → блокировки: флаг сессии (holder) и непоказанный pending → задержка ~0.8 с (даём экрану отрисоваться) → перепроверка pending после задержки (за окно ожидания состояние могло измениться; при несовпадении — тихий пропуск, повтор при следующем возврате) → закрытие флага сессии ДО запуска флоу (даже при ошибке повторных авто-запросов в этой сессии не будет) → отметка milestone пройденным атомарно со снятием совпадающего pending (D3) → запуск SDK-флоу → лог аналитического исхода. Жизненный цикл pending замыкается в момент запуска флоу: milestone уже в passed, совпадающий pending снят атомарно (D3) — отдельный сброс после завершения флоу не нужен, состояние «pending ∈ passed» невозможно (D3). Без снятия pending новая сессия повторила бы показ пройденного milestone (нарушение спечного «Пройденный milestone не повторяется»), а правило D2 «пока pending существует → не запрашивать» навсегда заблокировало бы планирование milestone 5/15, который спека гарантирует («будет запланирован при следующем создании записи после показа текущего pending»). Ошибки — тихо, без UI и фолбэка (спека).
- **Кнопка** — `MoreScreen`: без изменений, продолжает открывать `ACTION_VIEW` на страницу отзывов; SDK-флоу кнопкой не инициируется (D4).
- **Аналитика** — четвёртый тип события в sealed interface `AnalyticsEvent` (прецедент расширения модели; сейчас ровно три типа): `data class ReviewAutoRequest(val outcome: ReviewAutoRequestOutcome, val errorType: ReviewErrorType? = null) : AnalyticsEvent`, где `ReviewAutoRequestOutcome` — новый enum (`SHOWN`, `ERROR`; UPPER_SNAKE wire-значения, канон — `UserActionType`), а `ReviewErrorType` переиспользуется из `domain/review/` (одна классификация ошибок на домен и аналитику; зависимость `analytics/` → `domain/` легальна — обратная запрещена guard-тестом). Номер milestone в событие не входит (спека). `FirebaseAnalyticsProvider` — новая ветка `when`: событие `review_auto_request` с параметрами `outcome` и (при ошибке) `error_type`; Noop-провайдер изменений не требует.
- **Строки** — не добавляются: SDK рисует свой UI, кнопка использует существующую ссылку без изменений.

### D6. DI: сборка через композиционный корень (без AppModule)

В проекте manual DI без модуля зависимостей (`di/` намеренно не создаётся), поэтому wiring — по существующим точкам:

- `MyWorkoutsApplication` — три новых process-singleton'а по образцу существующих `lazy`-свойств (счётчик по всему change; на wiring-этапе 6.1 новых singleton'ов два — `ReviewCountersDataStore` создаётся уже на этапе 3.3 tasks): `ReviewCountersDataStore` (D3), `ReviewFlowLauncher` — через flavor-фабрику `ReviewFlowLauncherFactory.create(context)` с одинаковым FQN в `app/src/rustore/` и `app/src/github/` (D1), `ReviewSessionHolder` (in-memory, в `main` — от SDK не зависит, flavor-вариантов не имеет).
- `MainActivity` получает их из `application as MyWorkoutsApplication` и передаёт в `RootScreen` (у него уже `@Suppress("LongParameterList")` — явные параметры, без упаковки в контейнер); `RootScreen` прокидывает в приватный `AppNavHost`, тот — в destination-компоузаблы.
- Фабрики ViewModel: `EntryCreateViewModel.factory(...)` (вызов в `RootScreen.kt`) — + `isReviewEnabled = BuildConfig.RUSTORE_FEATURES`, `ReviewCountersDataStore`, `ReviewSessionHolder`; `ReviewMilestoneDecider` — stateless, инстанцируется внутри фабрики (прецедент — `ExportBackupUseCase` в `AppDataViewModel.factory`). `MainViewModel.factory(...)` (вызов в `NavDestinations.kt`) — + `isReviewEnabled`, `ReviewCountersDataStore`, `ReviewFlowLauncher`, `ReviewSessionHolder`. `AppDataViewModel.factory(...)` — + `ReviewCountersDataStore` для сброса.
- Кнопка «Оценить приложение» в `MoreScreen` не меняется.

### D7. Подключение зависимости

- Версия в `gradle/libs.versions.toml` (`rustoreReview = "10.5.2"` — проверена эталоном; допустим бамп на свежайшую стабильную при проверке дерева зависимостей, дефолт — 10.5.2), библиотека `rustore-review`, подключение `rustoreImplementation(libs.rustore.review)`: прямая версия без BOM — в проекте один SDK RuStore, BOM оправдан при появлении второго.
- Репозиторий `https://nexus-external.rustore.ru/repository/maven-rustore-exposed` — только в `dependencyResolutionManagement` в `settings.gradle.kts`: проект в режиме `FAIL_ON_PROJECT_REPOS`, репозиторий в `app/build.gradle.kts` сборка не пройдёт. Content-filter по группе `ru.rustore.sdk` (`exclusiveContent`/`content { includeGroup(...) }`), чтобы сторонний репозиторий не стал источником для остальных артефактов.
- Gotcha эталона: прямой gradle-вызов не подтягивает секреты — `signingConfigs` читает `KEYSTORE_FILE` из `.secrets/secrets.properties` с `checkNotNull` на этапе конфигурации, на чистом чекауте без `.secrets/` падает любая gradle-команда. Проверки дерева зависимостей и flavor-прогоны запускать после любой make-цели с секретами (например, `make build FLAVOR=rustore`).

### D8. Тестовая стратегия и прогон flavor-тестов (решение по `make test`)

- **Unit (домен, TDD — тесты до логики)**: milestone-решения — первый/пятый/пятнадцатый milestone, выбор наивысшего достигнутого непройденного, повтор в сессии, milestone с уже выполненным авто-запросом не повторяется, pending не перезаписывается, после всех порогов решений нет, сброс; контракт лаунчера на fake-реализациях.
- **Unit (данные)**: персистентность и сброс хранилища счётчиков.
- **Unit (ViewModel)**: `EntryCreateViewModel` — флаг `isReviewEnabled = true/false`, редактирование не инкрементит, holder сессии блокирует планирование; `MainViewModel` — отложенный показ на fake-лаунчере (задержка — виртуальным временем `testDispatcher`), тихая ошибка интерфейс не меняет, повторное срабатывание в сессии исключено, после показа pending сброшен и в новой сессии не повторяется.
- **Unit (flavor rustore)**: тесты классов из `app/src/rustore/` (SDK-лаунчер на MockK c fake-обёрткой менеджера) живут во flavor test source set `app/src/testRustore/java` — в общем `app/src/test/` они не скомпилируются под github-вариант (классы под тестом существуют только в rustore). MockK и корутинные тест-утилиты из `testImplementation` доступны во всех unit test-вариантах автоматически.
- **РЕШЕНИЕ (фиксируется): `make test` флагом FLAVOR не расширяется.** `make test` запускает агрегатную gradle-задачу `test`, а она при наличии product flavors выполняет unit-тесты всех вариантов (github+rustore, debug+release) — flavor-тесты из `app/src/testRustore/` попадают в штатный прогон и общий отчёт `scripts/test_report.py` без правки Makefile. Точечные прогоны в разработке — прямой gradle-вызов `./gradlew testRustoreDebugUnitTest --tests "<FQN>"` (правило «один прогон — один отчёт» сохраняется). Verify первой реализации: в выводе/отчёте `make test` присутствуют тесты RustoreDebug-варианта; если агрегат их вдруг не подхватит — flavor-прогон прямой gradle-задачей отдельной командой (fallback без правки Makefile). Правило «один прогон — один флейвор» остаётся для `make android-test` / `memory-check` / `build` / `apk` (FLAVOR там уже поддерживается).
- **SDK-ветка автотестами не покрывается** (эмулятор без RuStore) — ручная проверка на устройстве/эмуляторе с установленным RuStore; чек-лист ручной проверки — в tasks (8.3).
- **`make memory-check`** — задача трогает UI и ViewModel (новые зависимости у `MainViewModel`/`EntryCreateViewModel`).

## Risks / Trade-offs

- [Дневной лимит отображений регулируется на стороне RuStore: SDK-флоу может не показать форму даже при успешном вызове] → авто-режим тихо завершается; milestone помечается пройденным при запуске флоу (безопасно против повторных «пустых» вызовов). Кнопка SDK не вызывает — доковская рекомендация «не использовать кнопку как триггер» выполняется сама собой.
- [`Task.await()` SDK блокирует (CountDownLatch, доставка результата через main-looper): вызов на main-диспетчере = дедлок/ANR] → rustore-реализация лаунчера обязана оборачивать SDK-флоу в `withContext(Dispatchers.IO)` (урок эталона, подтверждён ANR на эмуляторе); юнит-фейки этот класс багов не ловят — только живой SDK в ручной проверке.
- [Новый сторонний maven-репозиторий — расширение supply chain] → content-filter по группе `ru.rustore.sdk`, официальный URL из документации SDK, версия зафиксирована в `libs.versions.toml`.
- [Неизвестные транзитивные зависимости SDK, конфликт версий или сетевой стек внутри SDK] → на этапе реализации проверить дерево зависимостей (`app:dependencies --configuration rustoreDebugRuntimeClasspath`); сетевой стек в приложении не появляется — взаимодействие идёт через приложение RuStore (второе исключение офлайн-правила, фиксируется в AGENTS.md).
- [Первый flavor source-set меняет устоявшийся паттерн «всё в main»] → задокументировать в docs/deployment.md; гард: github-вариант собирается без SDK-зависимости (компиляция и есть проверка изоляции).
- [minSdk SDK явно не заявлен в документации] → у проекта minSdk 26 — выше типовых требований RuStore SDK; проверить на этапе реализации, зафиксировать в docs/deployment.md при наличии ограничения.
- [Release-сборка с R8 (`isMinifyEnabled = true`) может требовать правил для SDK] → проверить `make apk FLAVOR=rustore`; при необходимости добавить правила в `app/proguard-rules.pro` (SDK обычно возит consumer-rules).
- [Ошибочная классификация исходов в аналитике исказит конверсию] → исходы фиксируются по фактическим результатам фаз SDK (подготовка/показ), а не по предположениям.

## Migration Plan

Обычная фича-ветка, релиз — штатным процессом rustore flavor (docs/deployment.md, `make rustore`). Миграций схемы БД нет. Откат — revert ветки: SDK-зависимость и flavor source-sets самодостаточны, обратной миграции данных не требуется (новый DataStore `review_counters` не читается старыми версиями). Разрывов совместимости формата бэкапа нет — фича его не затрагивает (счётчики в бэкап не входят и при импорте не восстанавливаются).
