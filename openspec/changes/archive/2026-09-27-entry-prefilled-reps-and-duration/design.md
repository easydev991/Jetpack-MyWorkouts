# Design

## Context

Экран записи — `EntryCreateScreen` + `EntryCreateViewModel`
(`ui/viewmodel/EntryCreateViewModel.kt`). Точка внедрения —
`onExerciseChange`: сейчас он синхронно сбрасывает `repsText`/
`durationSec` при смене типа измерения. Режим задаётся `entryId`
(`NO_ENTRY_ID` — создание); `EntryCreateUiState.weightText` имеет дефолт
`"0"` («без веса»). `ExerciseEntryDao` запросов истории не имеет;
`ExerciseEntry.workoutId` в MVP всегда `null` — история берётся по
`exerciseId` без привязки к тренировкам. Схема БД (v3) не меняется —
только новый SELECT. Существующий интерфейс `WorkoutDataRepository`
реализуют Room-репозиторий и несколько Fake-репозиториев в JVM-тестах —
новый метод добавляется во все.

## Goals / Non-Goals

**Goals:**

- Предзаполнение пустых reps/durationSec/weightText при выборе упражнения
  в режиме создания — по правилам spec-дельты.
- Защита от гонок: смена упражнения во время загрузки истории не даёт
  применить устаревший результат.

**Non-Goals:**

- Реактивная история (Flow) — предзаполнение одноразовое, на момент
  выбора упражнения.
- Предзаполнение подходов — никогда.
- Изменение поведения режима редактирования.
- Использование history-данных где-либо ещё (обзор, список записей).

## Decisions

**D1. Один запрос-снимок истории упражнения (DAO).**
`ExerciseEntryDao.historyForExercise(id): List<ExerciseEntryEntity>` —
`SELECT * FROM exercise_entries WHERE exercise_id = :id ORDER BY date DESC,
created_at DESC`. Упорядоченный снимок: «последняя запись» — первый
элемент; статистика веса (количество `weightKg > 0`, первая запись
с `weightKg > 0`) выводится из того же списка — без второго SQL-запроса.
`created_at DESC` — вторичный тай-брейк записей с одинаковым `date`
(в `date` уже есть время суток, поэтому основной порядок покрывает
«несколько записей в один день»). Альтернатива — отдельные агрегаты
(`COUNT`/`MAX`) или два запроса: больше SQL и чтений ради того же
результата; снимок проще и тривиально тестируется в
`ExerciseEntryDaoTest` (androidTest).

**D2. Репозиторий: `suspend fun exerciseHistory(exerciseId: Long):
Result<List<ExerciseEntry>>`.**
Образец существующих точечных операций: `Result` + try/catch в
`RoomWorkoutDataRepository`, маппинг `toDomain()`. Пустая история —
`success(emptyList())`. Альтернатива `Flow` — не нужна: одноразовое
предзаполнение, не реактивный UI. Метод добавляется в интерфейс и во все
Fake-реализации JVM-тестов (компилятор укажет список).

**D3. Предзаполнение в `onExerciseChange`: синхронный update + корутина.**
После существующего `mutableUiState.update` запускается
`viewModelScope.launch`: запрос истории → вычисление значений → условное
применение тем же `update`. Применение только при всех трёх условиях:
(а) `selectedExercise?.id` не изменился с момента запроса (id захватывается
до запуска), (б) целевые поля всё ещё не изменены пользователем (пустые
reps, `null` duration, `weightTouched == false` — D5), (в) режим
создания (`entryId == NO_ENTRY_ID`). Пока грузится — поля пустые
(текущий вид). Альтернатива — блокирующая загрузка до выбора: заморозит
UI ради копеечного индексного SELECT.

**D4. Расчёт значений — private-функции ViewModel, без нового use-case.**
Логика чистая и маленькая: «последняя запись» по measuredBy + правило
веса (`weighted * 2 > total`, значение — `weightKg` первой записи
с `weightKg > 0` в снимке). Покрывается JVM-тестами
`EntryCreateViewModelTest` через Fake-репозиторий — отдельный use-case
ради одной функции не нужен.

**D5. Условие применения веса — «поле не изменено пользователем».**
Дефолт поля — `"0"`, а `sanitizeWeight` превращает и очистку поля, и ввод
«0» обратно в `"0"` — строкой состояния «не тронуто» от «введён 0» не
отличить. В `EntryCreateUiState` добавляется флаг `weightTouched = false`,
выставляемый в `onWeightChange`; `onExerciseChange` и корутина
предзаполнения его не сбрасывают. Предзаполнение применяется, только пока
`weightTouched == false`: введённый пользователем «0» не перезаписывается,
как и любое другое введённое значение (spec-сценарий «Введённый
пользователем вес не перезаписывается»). Для reps/duration флаг не нужен —
пустая строка и `null` однозначно означают «поле не тронуто».

**D6. Предзаполнение не зависит от видимости полей.**
Значения пишутся в UiState независимо от `is*FieldVisible` — существующее
правило «скрытые поля продолжают учитываться» (entry-settings-screen)
менять не нужно. Типозависимое поле всегда видимо (канон), поэтому
развилка касается только веса; поведение закреплено spec-сценарием
«Скрытое поле веса предзаполняется на общих правилах».

## Risks / Trade-offs

- [Снимок устаревает: запись добавится после загрузки истории] →
  Приемлемо: предзаполнение — подсказка, а не инвариант; следующее
  открытие экрана увидит свежие данные.
- [Гонка «запрос → смена упражнения → результат»] → D3: тройная проверка
  перед применением; состояние «пока грузится» совпадает с текущим видом.
- [Новый метод интерфейса ломает компиляцию всех Fake-репозиториев] →
  Ожидаемая правка: во Fake — поле/параметр с историей по умолчанию
  `emptyList()`; компилятор перечислит затронутые файлы.
- [Detekt: рост числа методов репозитория] → `TooManyFunctions` на
  интерфейсе уже подавлен осознанно; `LongMethod`/`ComplexCondition` в VM
  не ожидаются — при появлении предупреждения исправляется до завершения
  задачи (лимит `maxIssues: 5` не повышается).

## Migration Plan

Без миграций: схема БД не меняется, новый код включается с релизом.
Откат — реверс коммита.
