## Context

Слой данных (`workout-data-layer`, дельты `workout-data-deletion`) хранит
каталог упражнений `(id, name, category, isCustom, comment, createdAt)`
и записи о выполнении. Категория не кодирует способ измерения нагрузки:
планка (CORE) — на время, скручивания (CORE) — на повторы. Мотивация —
в proposal.md (Why). Будущий экран создания записи будет ветвиться по
`measuredBy` (Change `entry-create-screen`).

Ограничение, снятое заказчиком: приложение не в релизе, пользователей
нет — миграция БД не пишется.

## Goals / Non-Goals

**Goals:**

- Каждое упражнение каталога (стандартное и пользовательское) несёт тип
  измерения `REPS`/`TIME`, доступный при чтении каталога.
- 13 стандартных упражнений размечены при prepopulate: планка и скакалка —
  `TIME`, остальные — `REPS`.
- Существующие тесты каталога расширены, контракт «ровно 13» сохранён.

**Non-Goals:**

- Валидация соответствия «measuredBy ↔ заполненные поля записи» — это
  будущий UI; `EntryValidator` не меняется.
- Миграция БД и bump версии — см. Decision 3.
- UI выбора типа при создании упражнения — будущий change экрана
  управления упражнениями; API слоёв ниже уже готово его принять
  (`measuredBy` передаётся через модель `Exercise`).

## Decisions

### Decision 1: enum в домене, строка в entity — как у `category`

`domain/model/ExerciseMeasuredBy.kt`: `enum class ExerciseMeasuredBy {
REPS, TIME }`. `ExerciseEntity` хранит колонку `measured_by` строкой
(`REPS`/`TIME`), маппинг — в `Mappers.kt`, рядом с существующим
маппингом категории.

Альтернативы отклонены:
- `Boolean isTimed` — короче, но ломает консистентность с паттерном
  `category` (enum остаётся в домене, entity — строки; design.md
  Decision 2 из `workout-data-layer`) и потребует смены типа поля при
  будущем расширении (например, `DISTANCE` для бега).
- Enum прямо в entity (`TypeConverter`) — типизирует data-слой доменом,
  уже отклонено проектом для `category`.

### Decision 2: `Exercise.measuredBy` со значением по умолчанию `REPS`

`val measuredBy: ExerciseMeasuredBy = ExerciseMeasuredBy.REPS` —
дефолт в конструкторе доменной модели. Все существующие вызовы
`Exercise(...)` (тесты, будущий CRUD упражнений) продолжают компилироваться
без правок; «большинство упражнений — на повторы» фиксируется на уровне
типа. Явный `TIME` передается параметром.

### Decision 3: версия БД остаётся `1`, миграция не пишется

Приложение не в релизе, пользователей нет — пишем `ALTER TABLE`-миграцию
в никуда. Схема `1.json` перегенерируется ksp-экспортом, новый файл
коммитится. Версия остаётся `1`: свежие установки создают БД сразу
с `measured_by`.

Побочный эффект: существующие дев-установки упадут с
`IllegalStateException` (identity hash схемы изменился) — лечится
переустановкой/очисткой данных приложения. Это осознанно дешевле
поддержки миграционного кода без единого пользователя.

### Decision 4: prepopulate размечает типы в существующем raw-SQL

`StandardExercise` получает поле `measuredBy`; `standardExercises(...)`
размечает 13 пар: планка и скакалка — `TIME`, остальные 11 — `REPS`.
Callback `WorkoutDatabase.create` добавляет значение в `INSERT` —
тот же raw SQL, что и сейчас (callback не имеет доступа к DAO).

### Decision 5: репозиторий и валидатор записей не меняются

`RoomWorkoutDataRepository.addExercise/updateExercise` принимают
`Exercise` — новое поле проедет через них без правок. `EntryValidator`
не знает про `measuredBy` (спека: «Слой данных не навязывает
соответствие»). DAO-интерфейсы не меняются: `ExerciseDao` работает
с entity целиком.

## Risks / Trade-offs

- [Дев-установки падают после обновления схемы] → переустановка
  приложения; тестовые данные на девайсах разработчика пропадут —
  приемлемо (Decision 3).
- [Забытая перегенерация `1.json` → расхождение схемы в репо] → задача
  в tasks.md: собрать проект и закоммитить обновлённый schema-JSON.
- [Тесты, фиксирующие состав полей entity/записей] → обновляются
  в этом же change; контракт «ровно 13 стандартных» не меняется,
  добавляется только разметка `measuredBy`.

## Migration Plan

1. Реализация → `make format && make lint && make test` →
   `make android-test` (эмулятор/девайс с переустановленным APK).
2. Перегенерированный `app/schemas/.../1.json` коммитится вместе
   с кодом.
3. Откат — revert коммита; данные БД на дев-девайсах после отката также
   требуют переустановки.
