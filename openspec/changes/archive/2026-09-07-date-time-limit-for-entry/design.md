## Context

Экран создания записи (`EntryCreateScreen.kt`) уже имеет всё необходимое:
`EntryCreateViewModel` принимает `nowProvider: () -> Long` и использует его
в `initialState(nowMillis)` для дефолтных даты/времени. Пикеры — M3
`DatePickerDialog` + `DatePicker` (`DateField`) и `AlertDialog` + `TimePicker`
(`TimeField`) в `EntryCreateFields.kt`. Конвертация даты в millis пикера —
`localDateToPickerMillis` / `pickerMillisToLocalDate` (`EntryCreateFormatters.kt`),
обе работают в UTC-полночь. Мотивация — см. proposal.md, требования — см.
specs delta.

## Goals / Non-Goals

**Goals:**

- Запретить выбор момента записи позже момента открытия экрана.
- Зафиксировать момент открытия один раз при создании ViewModel.
- Блокировка даты — в самом пикере; клэмп времени — в ViewModel.

**Non-Goals:**

- Ограничение «не раньше некоторой даты» (минимум) — не требуется.
- Обработка гипотетических future-dated записей из dev/тестовых данных —
  вне скоупа (приложение до релиза, у пользователей таких записей нет).
- Изменение форматов отображения даты/времени.

## Decisions

### Decision 1: Блокировка в пикере + молчаливый клэмп, не валидация

Дата: `DatePickerState.selectableDates` — недоступную дату нельзя выбрать
вовсе, UI сам показывает её недоступной. Время: у M3 `TimePicker` нет
встроенного ограничения, поэтому клэмп в `EntryCreateViewModel.onTimeChange`.

Альтернатива — валидация с ошибкой при сохранении: хуже UX (ошибка в конце
вместо предотвращения) и противоречит существующему стилю (санитайзинг
числовых полей тоже молча нормализует ввод). Рекомендация — блокировка/клэмп.

### Decision 2: Сравнение по локальной дате, не по «сырым» millis

`DatePicker` работает в UTC-millis; `selectableDates.isSelectableDate(millis)`
получает UTC-полночь дня. Сравнивать надо по локальной дате открытия:
граница = `localDateToPickerMillis(openLocalDate)`; `isSelectableDate(millis)`
проверяет `millis <= граница` — наивное сравнение с `System.currentTimeMillis()`
ломает сегодняшний день при смещении зон.
Переиспользуем существующие `localDateToPickerMillis` / `pickerMillisToLocalDate`.

### Decision 3: Момент открытия живёт в ViewModel

`EntryCreateViewModel.initialState` сейчас вызывает `nowProvider()` инлайн и
передаёт момент только параметром в `initialState(nowMillis)` — поля с
моментом в ViewModel нет. Change добавляет поле `openMomentMillis` в
ViewModel (инициализация один раз в конструкторе из `nowProvider()`) и
одноимённое поле в `EntryCreateUiState` с дефолтом (прецедент —
`date: LocalDate = LocalDate.now()` — иначе сломаются существующие
вызовов конструктора). Второго поля в UiState нет; локальную дату открытия
пикер считает по тому же паттерну, что `prefillState`/`initialState`.
Пересчитывать «сейчас» при каждом взаимодействии запрещено (spec-сценарий
«Момент открытия не пересчитывается»).

### Decision 4: Клэмп также в `onDateChange` при смене даты на день открытия

При смене даты на день открытия экрана уже выбранное время, оказавшееся
позже момента открытия, тоже клэмпится. Иначе достижим будущий момент:
сегодня 10:00 → сменить дату на вчера → выбрать 23:00 (клэмп не срабатывает,
дата ≠ день открытия) → вернуть дату на сегодня → запись снова в будущем.
Инвариант «дата = день открытия ⇒ время ≤ момент открытия» поддерживается
в обоих обработчиках — `onTimeChange` и `onDateChange`.

### Decision 5: Режим редактирования — без отдельной ветки и без клэмпа prefill

В пользовательских данных future-dated записей нет: единственный источник
записей — этот экран, который после change такие записи не создаёт.
Поэтому `prefillState` не требует клэмпа. Ограничения применяются к новым
выборам пользователя так же, как в режиме создания — общий код, отдельной
ветки нет (spec-сценарий «Редактирование старой записи не меняет её дату и
время»).

## Risks / Trade-offs

- [Часовые пояса: UTC-millis пикера против локального дня открытия] →
  сравнение только через `localDateToPickerMillis` локальной даты открытия
  (Decision 2); юнит-тест на границу дня в фиксированной зоне.
- [Молчаливый клэмп времени может удивить пользователя] → осознанный
  trade-off (Decision 1); значение в поле меняется на границе, что видно.
- [Экран открыт через полночь] → ограничение остаётся на момент открытия —
  это требование, не баг (spec-сценарий «Момент открытия не пересчитывается»).

## Migration Plan

Обычная фича-ветка, обратной совместимости данных не требует. Откат —
revert коммита.
