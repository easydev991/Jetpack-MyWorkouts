# Design: exercise-icon-mvp

## Context

Модель `Exercise` — data class из 8 полей (`id`, `name`, `category`,
`isCustom`, `comment`, `createdAt`, `measuredBy`, `isArchived`), хранится
в `ExerciseEntity` (таблица `exercises`, версия схемы БД — 2,
`fallbackToDestructiveMigration`, схема экспортируется в `app/schemas/`).
Prepopulate — тройка `StandardExercise` + raw SQL INSERT в seed-callback.
Бэкап v1 — ручная сериализация в `ExportBackupUseCase.buildBackupJson`
(паттерн `?: JSONObject.NULL` для опциональных полей) и парсинг в
`ImportBackupUseCase.parseBackupJson` (хелперы `optionalInt`/
`optionalString`/`optionalDouble`). Прецедент добавления поля —
`isArchived`: bump версии (1→2) вместо Migration.

Мотивация и скоуп — см. proposal.md; контракты поведения — см. дельты
спек (`workout-data`, `app-data-management`).

## Goals / Non-Goals

**Goals:**

- Поле `iconNumber: Int?` проходит весь data-путь: модель → entity → БД →
  мапперы → бэкап (экспорт/импорт/merge) → prepopulate.
- Обратная совместимость резервных копий в обе стороны (формат v1
  сохраняется).
- Ключ для будущих changes: добавление иконок-ресурсов, назначение
  стандартным, выбор в UI.

**Non-Goals:**

- Иконки-ресурсы и их отрисовка, назначение номеров стандартным
  упражнениям, UI-выбор иконки — отдельные будущие изменения.
- Валидация диапазона `iconNumber` (см. Decision 2).
- Миграция данных (деструктивный фоллбек остаётся до релиза).

## Decisions

### Decision 1: Bump версии БД 2 → 3 без Migration

Колонка `icon_number INTEGER` (nullable) добавляется в `ExerciseEntity`,
версия `WorkoutDatabase` поднимается 2 → 3. Прецедент `is_archived`
(bump 1 → 2): до первого релиза `fallbackToDestructiveMigration`
пересоздаёт базу с новым prepopulate, миграция не нужна. После релиза
деструктивный фоллбек заменяется миграциями (отдельное изменение).

Альтернатива — `Migration(2, 3)` с `ALTER TABLE ... ADD COLUMN`: не даёт
пользы до релиза (данные всё равно тестовые) и добавляет код, который
придётся удалять. Колонка без SQL DEFAULT (`defaultValue`), в отличие от
`is_archived`: default там был нужен, чтобы существующие строки при
неразрушающем добавлении оставались активными; здесь пересоздание
деструктивно, а nullable-колонка и так заполняется `NULL`.

### Decision 2: Диапазон `iconNumber` в MVP не валидируется

Хранилище и бэкап принимают любое `Int` (включая отрицательное) или
`null`. Альтернатива — проверка `>= 0` в репозитории/валидаторе:
отклоняется, потому что (а) набора иконок-ресурсов ещё не существует —
не с чем сверять верхнюю границу; (б) единственный потребитель поля —
будущий UI-слой, и именно он обязан безопасно обрабатывать значение без
соответствующего ресурса (fallback-иконка), иначе он был бы сломан и при
валидном, но устаревшем наборе ресурсов. Ограничение диапазона станет
осмысленным только вместе с ресурсами и вводится тем будущим изменением.

### Decision 3: Nullable-поле с Kotlin-дефолтом `null` во всех тройках

`Exercise.iconNumber: Int? = null`, `ExerciseEntity.iconNumber: Int? = null`,
`StandardExercise.iconNumber: Int? = null` — Kotlin-дефолты в конструкторах
(паттерн `measuredBy`/`isArchived`): все существующие именованные вызовы
(`Exercise(...)`, конструктор entity в тестах, `StandardExercise(...)` в
`standardExercises()`) продолжают компилиться без правок. Значения
стандартным упражнениям пока не проставляются — prepopulate пишет `null`.
Seed-callback дополняет INSERT колонкой `icon_number` со значением `NULL`:
явная колонка делает prepopulate-контракт полным относительно схемы и
оставляет будущему change единственную правку — подстановку значений в args.

Альтернатива — не трогать seed-callback (nullable-колонка заполнилась бы
`NULL` сама): отклонено, сырой SQL рядом с новой схемой должен
перечислять актуальный набор колонок, «неявный NULL» — ловушка для
следующего, кто добавит поле.

### Decision 4: Формат бэкапа — обратно совместимое расширение, версия остаётся 1

- Экспорт: `.put("iconNumber", exercise.iconNumber ?: JSONObject.NULL)` —
  поле пишется всегда (явный `null`, паттерн `comment`/`reps`), элемент
  `exercises` самодостаточен.
- Импорт: `iconNumber = obj.optionalInt("iconNumber")` — существующий
  хелпер возвращает `null` и для отсутствующего поля (старый бэкап),
  и для `JSONObject.NULL`. Отдельная ветка «файл до/после» не нужна.
- Версия не поднимается: старый файл валиден по-прежнему, а новый файл на
  старой версии приложения переносится как неизвестное поле — это уже
  гарантировано сценарием «Неизвестные поля игнорируются» существующей
  спеки `app-data-management`. Bump до 2 сломал бы импорт нового файла
  старыми версиями без какой-либо выгоды.

Альтернатива — не писать поле при `null` (экономия байт): отклонена —
ломает единообразие с остальными опциональными полями, которые
сериализуются явно, и усложняет diff-сравнение бэкапов.

### Decision 5: mergeBackup сохраняет `iconNumber` как есть

Вставка упражнения из файла идёт через существующий
`copy(isCustom = true, id = 0L)` — `iconNumber` проходит без изменений;
при дедупликации по имени существующее упражнение не трогается (уже так).
Ни веток, ни отдельных правил для `iconNumber` в merge не добавляется.

## Risks / Trade-offs

- [Деструктивный фоллбек: у тестеров с прежней сборкой пропадают данные
  при обновлении] → осознанно до релиза (прецедент `is_archived`);
  миграции вводятся отдельным изменением к релизу.
- [`iconNumber` из старого бэкапа/ручной правки БД указывает на
  несуществующий ресурс] → принято по Decision 2: контроль — обязанность
  будущего рендер-слоя; хранилище не знает о ресурсах.
- [Raw SQL в seed-callback может разойтись со схемой при опечатке] →
  prepopulate-контракт проверяется androidTest-ом `WorkoutDatabaseTest`
  (стандартный набор читается с `iconNumber = null`).
- [Старая версия приложения + новый бэкап] → вне скоупа этого изменения,
  покрыто сценарием «Неизвестные поля игнорируются» (см. Decision 4).

## Migration Plan

Bump версии схемы в одном коммите с кодом: приложение при первом запуске
после обновления пересоздаёт базу с prepopulate (деструктивно), экспорт
схемы `app/schemas/…/3.json` коммитится вместе с изменением. Откат —
git revert (данные тестеров не сохраняются, что приемлемо до релиза).
