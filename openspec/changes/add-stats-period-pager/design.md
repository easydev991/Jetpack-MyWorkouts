# Design

## Context

Вкладка «Статистика» экрана «Обзор» сейчас показывает одно окно: домен
считает его как `[today - (period.days - 1), today]` (`statsPeriodStart` в
`domain/usecase/ComputeCategoryStats.kt`), `computeCategoryStats` фильтрует
записи по этому диапазону, а `StatsUiState` несёт один набор агрегатов
(`categoryTotals`, `exerciseTotals`, `drillGroups`, `isEmpty`).
`OverviewViewModel` пересчитывает вкладки на каждой эмиссии потока записей;
`today` фиксируется при создании ViewModel.

Пикер периода — `SingleChoiceSegmentedButtonRow` на всю ширину во
всех трёх вкладках обзора (`StatsScreen.kt:477`, `RecordsScreen.kt:74`,
`ActivityScreen.kt:145`); выбранный вариант редизайна (12.11, владелец) —
этот же сегмент-контрол с подписью дат окна под ним.

Ограничения проекта: домен не знает об Android и о UI; `java.time` вместо
`kotlinx-datetime` (в проекте kotlinx-datetime нет); в заголовках месяцы
локализуются standalone-именами ICU с заглавной буквы (прецедент —
`MonthsHeader` в `ActivityScreen.kt:179`, разделитель —
`R.string.overview_months_separator`); в подписи дат окна используется
форматная форма ICU и капитализация не применяется (см. D6);
ручная DI без Hilt; Detekt-лимит 5 из 5 уже исчерпан существующими
находками; `HorizontalPager` в коде ещё не использовался, `foundation`
подтягивается транзитивно (BOM 2026.09.00).

Мотивация — proposal.md; требования — specs/overview-screen/spec.md.

## Goals / Non-Goals

**Goals:**

- Листать окна выбранного периода свайпом, не меняя тип периода, и всегда
  видеть в подписи, за какие даты построены данные.
- Не размножать стоимость расчёта: агрегаты по всем окнам считаются за
  один проход по записям.
- Сохранить существующие свойства: смена периода сбрасывает drill-down,
  состояние переживает поворот, но не переживает смерть процесса.

**Non-Goals:**

- Не менять семантику самих окон: они остаются скользящими и заканчиваются
  сегодня (решение владельца, 12.11) — календарные периоды не вводятся.
- Не переносить навигацию по окнам на вкладки «Активность» и «Рекорды»:
  там окна той же природы, но задача ограничена вкладкой «Статистика».
- Не менять визуал пикера периода — он остаётся сегмент-контролом на
  всю ширину; добавляется только строка подписи под ним.
- Не персистить смещение окна в preferences (как и сам период сегодня).
- Не трогать существующие capability-спеки, кроме `overview-screen`.

## Decisions

### D1. Окно — доменная величина, смещение — параметр расчёта

В домене появляется `StatsWindow(start: LocalDate, end: LocalDate)` и
extension-функция `fun StatsPeriod.window(today: LocalDate, offset: Int = 0):
StatsWindow` (объявлена в `domain/usecase/StatsWindow.kt` того же пакета —
членом enum `StatsPeriod` она не является): окно со смещением `o` — это
`[today - (o + 1) * days + 1, today - o * days]`
(смещение 0 — актуальное окно, заканчивающееся сегодня). Существующая
`statsPeriodStart` удаляется вместе с делегированием `computeCategoryStats`
(задача 1.4): после делегирования у неё не остаётся вызовов, а старт окна
берётся из `window(today).start`.

- Альтернатива: считать окно в UI-слое — отклонено: окно участвует в
  фильтрации записей и в подписи, то есть доменная величина; правило
  «`domain/` не знает об UI» из AGENTS.md.
- Альтернатива: заменить сигнатуру `computeCategoryStats(entries, period, today)`
  на `computeCategoryStats(entries, window)` — отклонено: ломает 18 существующих
  JVM-тестов и сигнатуру use-case ради косметики; вместо этого вводится
  отдельная функция (D2), а старая остаётся и делегирует ей.
- Видимость типа: `StatsWindow` — **публичный** data-класс в `domain/usecase/`
  (конвенция домена — публичные модели данных `CategoryTotal`,
  `CategoryStatsResult` в `ComputeCategoryStats.kt` при `internal`-функциях
  `statsPeriodStart`, `computeCategoryStats`). Публичность обязательна:
  `StatsUiState` — публичный data-класс в `ui/state/OverviewUiState.kt` и
  экспонирует границы окна в своём публичном API, а публичное свойство
  internal-типа не компилируется. Функции, работающие с окном
  (`StatsPeriod.window`, `computeCategoryStatsWindows`), остаются `internal` —
  их видимость не выходит за пределы модуля.

### D2. Агрегаты всех окон считаются за один проход

Ключевое наблюдение: окна — непересекающаяся разбивка прошлого, поэтому
запись с отставанием `k` дней от сегодня принадлежит ровно одному окну —
`o = k / days` (целочисленное деление). Значит, агрегаты по всем окнам
считаются за один проход по записям с раскладкой по корзинам, а не
`окон × записей`.

- Записи с датой позже сегодня отбрасываются до раскладки по корзинам —
  как в `computeCategoryStats` (`!day.isAfter(today)`): иначе целочисленное
  деление отрицательного отставания (`-1 / 7 == 0`) отнесло бы запись
  «завтра» к смещению 0, то есть к актуальному окну.
- В домене появляется `computeCategoryStatsWindows(entries, period, today):
  Map<Int, CategoryStatsResult>` — ключ — смещение окна; существующая
  `computeCategoryStats` делегирует ей и берёт смещение 0 (поведение и
  тесты не меняются).
- Контракт карты: ключи — все смещения от `0` до `maxOffset` включительно
  (`maxOffset` — предельная глубина листалки, D3); окно без записей даёт
  пустой `CategoryStatsResult` (пустые списки и карты), а не отсутствующий
  ключ. Экран читает агрегаты своей страницы по ключу и не заводит
  отдельного состояния «страница без записей».
- Ключ `0` присутствует всегда: если записей с датой ≤ today нет — в том
  числе когда все записи датированы позже сегодня — карта содержит
  единственный ключ `0` с пустым результатом. Иначе делегирование
  `computeCategoryStats` к смещению 0 ничего бы не нашло.
- Альтернатива: считать агрегаты только для текущего окна и до-страницы
  по мере надобности — отклонено: страницы пагера дорисовываются при свайпе,
  пустая страница во время жеста выглядит как сбой; ленивая догрузка
  потребовала бы отдельного состояния загрузки на страницу.
- Альтернатива: считать агрегаты постранично с кэшем — отклонено: тот же
  результат сложнее: кэш надо инвалидировать при каждой эмиссии записей.

### D3. Глубина листалки ограничена самой ранней тренировкой

Максимальное смещение `maxOffset = max(0, floor(daysBetween(earliest, today) / period.days))`,
где `earliest` — минимальный календарный день среди записей, которые
попадают в расчёт (даты ≤ today; записи позже сегодня в глубину листалки
не входят — они отбрасываются и в `computeCategoryStatsWindows`, D2).
Окно со смещением `o` пересекается с историей тогда и только тогда, когда
`o ≤ maxOffset`; при `o = maxOffset` окно содержит даты от `earliest` до
своего конца. Если записей с датой ≤ today нет — в том числе когда все
записи датированы позже сегодня — `maxOffset = 0`: листалка состоит из
одного актуального окна, смещение всегда 0.

- `earliest` для видимости периодов пикера по-прежнему считается по всем
  записям, включая будущие, — как в `visibleStatsPeriods`
  (`ui/viewmodel/OverviewViewModel.kt:136`); для глубины листалки берутся
  только записи с датой ≤ today.
- Единственный источник глубины листалки — контракт доменной
  `computeCategoryStatsWindows`: карта содержит все смещения `0..maxOffset`
  (D2), и ViewModel берёт `pageCount` из её ключей. Отдельного расчёта
  `maxOffset` в UI-слое нет — иначе правило «записи ≤ today» разошлось бы
  с расчётом агрегатов, а отрицательный `maxOffset` уводил бы индекс
  пагера за границу.
- Альтернатива: фиксированная глубина листалки (например, 12 страниц) —
  отклонено: показывала бы пустые окна и требовала бы заглушек.

### D4. Порядок страниц: актуальное окно — справа

По требованию владельца (решение 12.11): свайп содержимого **вправо**
открывает более раннее окно, свайп влево — более позднее. В дефолтном
`HorizontalPager` (`reverseLayout = false`, LTR) перетаскивание содержимого
влево увеличивает индекс страницы, поэтому содержимое, уходящее вправо,
уменьшает индекс. Чтобы свайп вправо вёл в прошлое, более ранние окна
должны лежать левее актуального, а само актуальное окно — на последней
странице: `pageIndex = maxOffset - offset`, где `maxOffset` — предельная
глубина листалки (D3). Свайп влево (к более позднему окну) от актуального
окна упирается в последнюю страницу — «следующего окна не существует»
выполняется самим пагером, без отдельных проверок.

- `reverseLayout` не используется: пагер остаётся в обычном порядке, его
  страницы идут слева направо по убыванию смещения (левее — более ранние
  окна).
- Альтернатива: актуальное окно на первой странице (`pageIndex = offset`) —
  отклонено: в дефолтном пагере свайп влево увеличивает индекс страницы,
  то есть при таком маппинге свайп влево уводил бы к более позднему окну, а
  к прошлому пришлось бы свайпать вправо; при выбранном владельцем
  направлении (палец вправо — в прошлое) маппинг должен быть обратным.
- Альтернатива: развернуть порядок через `reverseLayout = true` — отклонено:
  зеркалит и раскладку, и направление скролла самого пагера, из-за чего
  пришлось бы зеркалить и описание раскладки; при этом раскладку контента
  страницы он не меняет (в отличие от `LocalLayoutDirection`).
- Альтернатива: развернуть порядок через `LocalLayoutDirection` — отклонено:
  зеркалит раскладку самого контента (донат, легенда, список записей).

### D5. Состояние: двумерное, без персистентности

В `OverviewUserState` добавляется `statsWindowOffset: Int = 0`; в
`StatsUiState` — `windowOffset`, границы текущего окна (`StatsWindow`) и
карта агрегатов по смещениям (`statsByOffset: Map<Int, CategoryStatsResult>`),
из которой экран читает данные своей страницы.

- Плоских полей `categoryTotals` / `exerciseTotals` / `drillGroups` в
  `StatsUiState` не остаётся: единственный источник агрегатов — карта
  `statsByOffset`. Плоскими остаются `period`, `visiblePeriods`,
  `selected` и `categoryColors` — от окна они не зависят. Экран и его
  вспомогательные функции (`donutSlices`, `legendItems` в `StatsScreen.kt`)
  получают `CategoryStatsResult` своей страницы, а не `StatsUiState`.
- Смена типа периода сбрасывает смещение в 0 (актуальное окно) — как
  сбрасывается drill-down; иначе пользователь оказывается в окне, которое
  для нового типа может не существовать.
- Прокладка действия смены окна по цепочке экрана: `OverviewViewModel.selectStatsWindow(offset)`
  → `OverviewScreenActions.onStatsWindowChange` (`ui/screens/overview/OverviewScreen.kt:51–57`) →
  `OverviewScreen` (`:83`) → `StatsScreen` (`:153–156`). Колбэк **без
  значения по умолчанию**: значение по умолчанию (`= {}`) сделало бы
  непроведённую прокладку тихой ошибкой — свайп не менял бы окно, а
  компиляция проходила бы. На время перехода, пока черновик
  `StatsPeriodPickerDrafts.kt` ещё существует и вызывает `StatsScreen`,
  используется временный дефолт, который удаляется вместе с черновиком
  (задача 4.4).
- Карта агрегатов по смещениям содержит все смещения `0..maxOffset`
  (контракт D2), поэтому у экрана всегда есть агрегаты и для окна без
  записей — пустой результат; отдельного состояния «пустая страница» не
  требуется.
- Отсутствующий ключ карты — тоже пустая страница: чтение идёт с дефолтом
  (пустой `CategoryStatsResult` — пустые списки и карты), а не через
  обращение к отсутствующему ключу. Дефолтное `StatsUiState()` — до первой
  эмиссии потока (`initialValue = OverviewUiState()`,
  `ui/viewmodel/OverviewViewModel.kt:181`) — содержит пустую карту и потому
  трактуется как пустое окно: показывается подсказка «Нет тренировок за
  выбранный период» — как в существующем тесте `OverviewScreenTest`
  (строки 158–175).
- Признак пустоты — производная от карты: окно без записей даёт запись с
  пустым `drillGroups`, и экран считает пустоту своей страницы по записи
  карты для её смещения — например, `statsByOffset[offset]` с пустым
  `drillGroups`. Отдельного поля `isEmpty` в `StatsUiState` не остаётся
  (сейчас оно считается как `stats.drillGroups.isEmpty()` для актуального
  окна — `ui/viewmodel/OverviewViewModel.kt:156`) — на свайпнутой пустой
  странице показывается подсказка «Нет тренировок за выбранный период».
- Смещение ограничено глубиной истории: `maxOffset` считается от самой
  ранней записи (D3), поэтому удаление ранних записей уменьшает его —
  смещение прижимается к новой границе: `offset = min(offset, maxOffset)`
  (при `maxOffset = 0` — `offset = 0`; `maxOffset` неотрицателен — D3).
- Смена окна свайпом сбрасывает drill-down к обзору категорий (по сценарию
  «Свайп по окнам сбрасывает drill-down» требования «Drill-down категории
  в статистике»).
- Смещение не персистится в preferences — согласуется с уже действующим
  требованием «Период и drill-down не персистятся»; переживает только
  поворот экрана (ViewModel).

### D6. Подпись дат — чистая функция в `ui/util`

Новый файл `ui/util/StatsWindowFormatter.kt` по образцу `SectionDateFormatter.kt`:
чистая функция `formatStatsWindowLabel(window, period, locale, separator)`
(тестируется на JVM) и композиционная обёртка, берущая локаль из
`LocalConfiguration.current.locales[0]` и разделитель из
`R.string.overview_months_separator`.

Форматы (выбраны владельцем 12.11): «День» — дата дня в формате
`dd.MM.yyyy` («12.11.2026»); остальные — диапазон дат окна: внутри одного
месяца — «6 – 12 ноября», через месяц — «29 октября – 4 ноября», через
год — с годом в обеих границах («13 ноября 2025 – 12 ноября 2026»).
Правило года общее для «Недели», «Месяца» и «Года»: год в обеих границах —
когда границы окна в разных календарных годах; окно, целиком лежащее в
одном году, — без года.
Названия месяцев — форматная форма ICU (не standalone):
`Month.getDisplayName(TextStyle.FULL, locale)` — в ru это родительный
падеж («ноября»), в en — «November» (в en форматная и standalone-форма
совпадают). Standalone-форма («ноябрь») в подписи не применяется: в ru
дата с числом требует родительного падежа («6 – 12 ноября»), а
standalone-имя без числа («Ноябрь») уместно только как самостоятельный
заголовок. Капитализация из `MonthsHeader`
(`replaceFirstChar { it.uppercase(locale) }`) в подписи не применяется —
в заголовке месяцев месяц часть заголовка раздела, в подписи часть даты.
Подпись локализована ru/en без новых строковых ресурсов; числовой формат
дня не зависит от локали.

- Альтернатива: `DateTimeFormatter.ofPattern("d MMMM")` — отклонено: один
  шаблон не покрывает все формы подписи (короткая граница «6» без месяца
  при границах в одном месяце, год только у обеих границ), а части
  подписи собираются вручную; название месяца берётся точечно —
  `Month.getDisplayName(TextStyle.FULL, locale)`.
- Альтернатива: standalone-имена ICU (`TextStyle.FULL_STANDALONE`) —
  отклонено: в ru даёт именительный падеж («6 – 12 ноябрь»), неграмматично
  для даты с числом; standalone уместен для самостоятельных заголовков
  месяцев (прецедент — `MonthsHeader`,
  `ui/screens/overview/ActivityScreen.kt:189`).
- Альтернатива: новые строковые ресурсы под каждый вариант подписи —
  отклонено: месяцы уже локализованы ICU, ресурсы дали бы дублирование ICU.

### D7. Экран: пикер и подпись над пагером

`StatsScreen` (портрет и ландшафт) строится как: пикер периода и
подпись дат окна — фиксированный блок сверху, ниже — `HorizontalPager`,
страница которого рендерит существующий контент (донат, легенда, записи
drill-down) для своего окна.

- В портрете это меняет текущую раскладку: сегодня пикер живёт внутри
  `item(key = "header")` ленивого `LazyColumn`, а здесь выносится из
  скролла в фиксированный блок над пагером. Вертикальный скролл по
  устройству остаётся прежним (`LazyColumn` содержимого окна в портрете,
  независимые скроллы колонок в ландшафте), но меняется его состав:
  пикер и подпись дат больше не прокручиваются вместе с содержимым окна.
- Горизонтальное перетаскивание внутри `LazyColumn` drill-down не конфликтует
  с вертикальным скроллом: оси различаются, Compose разводит их сам.
- При смене типа периода и при изменении `maxOffset` (добавлена более
  ранняя запись) пагер переводится на страницу текущего окна
  (`LaunchedEffect` + `scrollToPage`), иначе индекс страницы перестал бы
  соответствовать смещению.
- При уменьшении `maxOffset` (удаление самых ранних записей) смещение
  прижимается к новой границе (см. D5), и пагер переводится на страницу
  прижатого смещения — иначе индекс страницы вышел бы за `pageCount`.
- Источник истины — смещение в состоянии (`OverviewUserState`,
  `OverviewViewModel`, D5): пагер только отображает окно, индекс страницы
  источником смещения не является. Программная синхронизация
  (`LaunchedEffect` + `scrollToPage`) при смене типа периода и при изменении
  `maxOffset` смены окна не инициирует: событие аналитики и сброс
  drill-down вызываются только пользовательским свайпом (D8).
- Механизм различения пользовательского свайпа и программной прокрутки
  (закрывает вопрос, оставленный ревью): смена окна обрабатывается в
  обработчике «страница остановилась» (`settledPage`) и сравнивается со
  смещением в состоянии — `settledPage != pageOf(state.windowOffset)` означает
  пользовательский свайп. Чтобы сравнение не давало ложного события, три
  условия выполняются по построению:
  - `initialPage` пагера = страница текущего смещения (`pageOf(offset)`), а
    не 0: при первом показе и после поворота экрана пагер открывается сразу
    на нужной странице, и первый «settle» совпадает со смещением;
  - любая программная прокрутка (`scrollToPage`) выполняется под флагом
    синхронизации, который снимается после следующего «settle»: событие
    смены окна в этот промежуток не обрабатывается;
  - при изменении `pageCount` (смена типа периода, появление или удаление
    ранних записей) страница принудительно приводится к странице текущего
    смещения — и до, и после изменения `pageCount`, поэтому «settle» с
    промежуточным индексом не возникает.
- Порядок страниц — обратный смещению (D4): страница окна со смещением `o` —
  `pageOf(o) = maxOffset - o`, то есть актуальное окно (`o = 0`) — последняя
  страница. Начальная страница пагера — `pageOf(state.windowOffset)`, при
  первом показе это последняя страница листалки.

### D8. Аналитика: отдельное действие пользователя

Свайп фиксируется новым `UserActionType.SELECT_STATS_WINDOW` со значением —
смещением окна строкой («1», «2», …): значение события — строка
(`AnalyticsEvent.UserAction.value: String?`, провайдер пишет его через
`putString("value", …)`), поэтому смещение передаётся десятичной записью.
Событие пишется только при пользовательском свайпе: программная
синхронизация страницы пагера (D7) его не вызывает. Это следствие D7
(программная синхронизация не обращается к ViewModel), а не отдельная
ветка в нём: в VM-тесте проверяется сам вызов `selectStatsWindow(offset)`
и значение события.
Существующий `SELECT_STATS_PERIOD`
со значениями `day|week|month|year` не переиспользуется: его wire-контракт
не меняется. Спека событийной модели аналитики в проекте есть —
требование «Событийная модель аналитики» в
`openspec/specs/crash-reporting/spec.md`:
идентификатор действия — строка в UPPER_SNAKE_CASE, значение опциональное.
Новое действие со значением-смещением ей соответствует, поэтому
изменения требований не требуются — факт фиксируется в design.
Требование «Логирование пользовательских действий» той же спеки отсылает
к сценариям, но его сценарий «Полный перечень логируемых действий» не
является исчерпывающим перечнем: в нём уже нет ранее заведённых
действий `SELECT_OVERVIEW_TAB`, `SELECT_STATS_PERIOD`,
`SELECT_STATS_CATEGORY`, `SELECT_RECORDS_MODE`, `SELECT_ACTIVITY_PERIOD`,
`SELECT_CATEGORIES_TAB`. Поэтому новое действие в этот перечень не
добавляется, а существующие capability-спеки задача не трогает
(Non-Goals).

### D9. Зависимости

`HorizontalPager` живёт в `androidx.compose.foundation`, который сейчас
подтягивается транзитивно через material3. Зависимость объявляется явно
через version catalog: алиас `androidx-compose-foundation` в
`gradle/libs.versions.toml` (без версии — версию задаёт BOM, как у
остальных compose-алиасов) и строка
`implementation(libs.androidx.compose.foundation)` в
`app/build.gradle.kts` — транзитивная зависимость не должна быть частью
контракта кода.

## Risks / Trade-offs

- [Карта агрегатов по всем окнам растёт с историей] → Окна — разбивка
  прошлого, суммарный объём данных равен объёму записей (как сейчас),
  количество корзин — `daysBetween/days`; дополнительной памяти сверх
  сегодняшнего расчёта не появляется.
- [Пагер остаётся на неверной странице при смене типа периода или при
  появлении более ранней записи] → `pageCount` задаётся лямбдой, позиция
  принудительно синхронизируется `LaunchedEffect` со смещением окна.
- [Удаление самых ранних записей сокращает листалку, а текущее смещение
  оказывается за новой границей] → Смещение прижимается к границе
  (`offset = min(offset, maxOffset)`, D5), страница пагера синхронизируется
  с прижатым смещением (D7).
- [Горизонтальный свайп конфликтует с вертикальным скроллом списка записей
  drill-down] → Оси различны; при необходимости (проверка на устройстве)
  пагер останавливается на вертикальном скролле.
- [Смещение окна не сохраняется между запусками приложения] → Осознанное
  ограничение, согласованное с существующим требованием о неперсистентности
  периода; пользователь всегда начинает с актуального окна.
- [Подпись дат занимает строку на экране с плотной раскладкой] → Строка
  вторичного текста (`bodySmall`) под пикером; при менее чем двух
  видимых периодах пикер скрыт, подпись остаётся.
- [Бюджет Detekt исчерпан: лимит 5 из 5] → Пять существующих находок уже
  выбирают лимит `maxIssues: 5` (`config/detekt/detekt.yml`; находки —
  `RootScreen.kt`: CyclomaticComplexMethod, LongMethod, TooManyFunctions,
  `MainScreen.kt` и `NavDestinations.kt`: LongParameterList), поэтому любая
  шестая валит `make lint`. Новая логика (пагер, страница окна, подпись
  дат) выносится в отдельные small-композиции и файлы, чтобы не растить
  существующие `StatsScreenPortraitBody` (48 строк) и
  `StatsScreenLandscapeBody` (59 строк) за порог LongMethod (60) — числа
  в метрике detekt (тело функции без пустых строк и комментариев);
  ландшафтное тело у порога, поэтому новый код в него не добавляется.
  Если находка всё же появилась — сначала снижается счётчик существующих
  находок (рефакторинг `RootScreen.kt`); лимит не повышается (AGENTS.md).
