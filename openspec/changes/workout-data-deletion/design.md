## Context

Слой данных уже создан в `workout-data-layer`: доменные модели,
Room-сущности, DAO, `WorkoutDatabase` (схема v1, exportSchema=true),
`RoomWorkoutDataRepository` с `Result`-API и валидатором. FK
`exercise_entries.exerciseId → exercises.id` объявлен с
`onDelete = NO_ACTION` (Decision 3 заархивированного
`workout-data-layer`, см. `archive/2026-09-02-workout-data-layer/design.md`),
что даёт SQLite-уровневую гарантию отката `DELETE FROM exercises` при
наличии ссылок. `RoomWorkoutDataRepository` уже использует
`Result` с `try/catch` для проброса исключений Room в `Result.failure`
по конвенции `AGENTS.md`.

## Goals / Non-Goals

**Goals:**

- Расширить DAO и репозиторий методами удаления по идентификатору.
- Реализовать бизнес-правила запрета удаления стандартных упражнений
  и упражнений с историей через `Result.failure`, без проброса
  низкоуровневых исключений.
- Сохранить идемпотентность удаления записей (повторный `deleteEntry`
  на отсутствующем id — не ошибка).
- Не менять схему БД (никаких миграций).

**Non-Goals:**

- UI, ViewModel, экран удаления — отдельный change.
- CASCADE-удаление, мягкое удаление (`isDeleted`) — отклонены по
  итогам анализа в основном диалоге (теряется история / мусор
  в `SELECT`).
- Bulk-удаление, undo, корзина — YAGNI для MVP.

## Decisions

### Decision 1: DAO-методы — `deleteById` через `@Query` с `suspend`

Добавляем в каждый DAO:

```kotlin
@Query("DELETE FROM exercises WHERE id = :id")
suspend fun deleteById(id: Long)
```

Используем `@Query` вместо `@Delete(entity)`, потому что нам нужен
именно «удалить по id, идемпотентно» — `@Delete` ожидает managed-entity,
а DAO-метод не имеет доступа к доменным моделям (entity не экспонируется).
`@Query DELETE WHERE` для отсутствующего id — успех без эффекта
(стандартное поведение SQL), что соответствует спеке для записей.
Альтернатива (`@Delete` + `findById` + удаление) — лишний round-trip
и лишняя точка отказа при race condition.

### Decision 2: Репозиторий — два метода с разными правилами

```kotlin
suspend fun deleteExercise(id: Long): Result<Unit>
suspend fun deleteEntry(id: Long): Result<Unit>
```

`deleteEntry` — обёртка над DAO, `try/catch` ловит всё и превращает
в `Result.failure` (на случай нештатных ошибок БД).

`deleteExercise` — двухшаговый:

1. Читаем упражнение (`getById`). Если отсутствует — `Result.failure`
   с сообщением «упражнение не найдено» (вызов на несуществующий id —
   не идемпотентная операция, в отличие от записи: пользователь явно
   указывает цель удаления, отсутствие цели — ошибка).
2. Если `isCustom == false` — `Result.failure` с сообщением
   «стандартное упражнение нельзя удалить».
3. Вызываем `dao.deleteById(id)` под `try/catch`. `SQLiteConstraintException`
   (FK-нарушение) переводим в `Result.failure` с сообщением
   «у этого упражнения есть записи, удалите их сначала». Прочие
   исключения — generic `Result.failure`.

Альтернатива «удалять сразу, ловить исключение и смотреть `isCustom`» —
отклонена: race condition (между чтением и удалением запись может
появиться) плюс смешение слоёв (бизнес-правило реализовано через
исключение, а не явную проверку).

### Decision 3: Никаких миграций

FK `NO_ACTION` уже в схеме v1. Поведение при удалении, которое
требует спека, реализуется поверх существующего FK без его изменения.
Экспортированная схема `app/schemas/.../1.json` остаётся актуальной.

## Risks / Trade-offs

- **Гонка между `getById` и `deleteById`** → узкое окно, но не исключено.
  → Если в окне появится запись, FK-исключение поймается в `try/catch`
  и станет `Result.failure` с тем же осмысленным сообщением — поведение
  деградирует до «не удалось удалить, у этого упражнения есть записи»,
  что совпадает с основным сценарием отказа. Дополнительной защиты
  не требуется.
- **`getById` возвращает `ExerciseEntity?`, домен маппится в репозитории** →
  контракт `ExerciseDao.getById` уже есть (зафиксирован в
  `archive/2026-09-02-workout-data-layer/tasks.md`): метод возвращает
  `ExerciseEntity`, а не доменный `Exercise`. Репозиторий читает
  `isCustom` через существующий `toDomain()` (`Mappers.kt`) — никаких
  новых запросов и мапперов не добавляется.
- **Локализация сообщений об ошибках** → в MVP сообщения на русском,
  хардкод в репозитории — осознанный выбор MVP, единичная точка
  формирования строки облегчает последующий маппинг на локализованные
  ресурсы в UI-слое.

## Migration Plan

Schema v1 не меняется. Деплой сводится к поставке новой сборки
с дополнительными методами DAO/репозитория; данные пользователей
не затрагиваются, миграции не требуются. Rollback безопасен:
новые методы не вызываются до появления UI-слоя в отдельном change.
