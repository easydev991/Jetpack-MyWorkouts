## Context

Главный экран вкладки «Тренировки» уже работает на реактивном потоке
`WorkoutDataRepository.entries()` (`MainViewModel.uiState`) и рендерит
плоский список `EntryListItem` через `LazyColumn` (`MainScreen` →
`EntryListItems`). Список уже отсортирован по дате убыванием на стороне
SQL. Доменная модель и слой данных сознательно остаются без изменений
(см. `proposal.md` — раздел «Impact / Что не меняется»).

Цель изменения — добавить визуальные секции по календарной дате и
сохранить существующее поведение (long-press меню, алерт удаления,
локализация ru/en, превью, edge-to-edge insets). Делаем это только
через уже подключённые Compose Foundation и `java.time`.

## Goals / Non-Goals

**Goals:**

- Разделить список на секции по `LocalDate` в системной зоне устройства.
- Сохранить порядок секций по убыванию даты и порядок записей внутри
  секции (готовый `entries` уже отсортирован убыванием по дате).
- Заголовки «Вчера» / дата в `dd.MM.yyyy`; секция «Сегодня» — без
  заголовка; локализация ru/en.
- Не сломать существующее поведение: long-press, удаление,
  `pendingDeleteId`-логика, превью, инсеты.
- Покрыть группировку быстрой JVM-проверкой; регрессию long-press /
  удаления / sticky-header — androidTest.

**Non-Goals** (проектные ограничения — в `proposal.md`, здесь —
только технические решения):

- Не вводим use-case для группировки: функция чистая и достаточно мелкая,
  чтобы жить рядом с экраном (`ui/screens/main/`).
- Не используем сторонние библиотеки для секций —
  `LazyListScope.stickyHeader` из Compose Foundation достаточно.
- Не вводим новые состояния `MainUiState` и не храним производные
  данные (секции) в state — рендерер считает их сам.

## Decisions

### Decision 1. Секции считаются на рендере, а не в ViewModel

Группировка `List<EntryListItem>` → `List<DateSection>` выполняется в
`SuccessBody` (`MainScreen`) через
`remember(success.entries) { groupEntriesByDate(success.entries) }`,
а не в `MainViewModel` и не в state.

**Контракт группировки:** внутри каждой `DateSection` записи идут
по убыванию `date` (epoch millis); гарантия держится явной
сортировкой входа по `date` убыванием внутри `groupEntriesByDate`
перед `groupBy`. Контракт не зависит от порядка входного списка
и не накладывает требований на SQL — функция самодостаточна
и переиспользуема без оговорок.

**Почему:**

- Секции — производное от `entries` 1:1: хранить их в
  `MainUiState.Success` значило бы дублировать данные и пересобирать
  их в каждом тесте/превью, создающем `Success`. `remember(entries)`
  кэширует результат до смены `entries` — стоимость та же, что
  у расчёта в `combine` на эмиссию, без лишнего поля.
- Группировка не зависит от «сегодня»: секции определяются только
  датами записей. Лейбл «Вчера» резолвится на рендере; у секции
  «Сегодня» заголовка нет вовсе (Decision 5); ViewModel не нужен
  ни источник даты, ни зона.
- Тестируемость: pure-функция `groupEntriesByDate` покрывается
  JVM-тестами без Compose; рендер-поведение — androidTest'ами
  (`MainScreenSectionsTest`).

**Альтернативы:**

- Хранить `sections` в `MainUiState.Success` и считать в `combine`.
  Отказ: производное поле в state — дубль `entries`, который
  приходится протаскивать через конструкторы в тестах и превью
  (итог ревью: поле удалено).
- Сделать use-case `GetEntriesByDateSectionUseCase`. Отказ: ради одной
  pure-функции добавлять слой use-case преждевременно (см. AGENTS.md —
  «реальные слои добавляй по мере фич, не плоди заранее»).

### Decision 2. `MainUiState.Success` остаётся парой `(entries, pendingDeleteId)`

State хранит только первичные данные: `entries: List<EntryListItem>`
(для empty-check и `pendingDeleteId`-lookup по `id`) и транзитный
`pendingDeleteId`. Секций в state нет — расхождение «entries vs
sections» невозможно по построению, потому что второго поля нет.

**Почему:**

- empty-check (`entries.isEmpty()`) — самый дешёвый путь к заглушке
  «Добавьте первую запись».
- При удалении последней записи секции она автоматически исчезает:
  реактивный Flow отдаёт новый `entries`, `remember(entries)`
  пересчитывает секции.
- Все существующие конструкторы `Success(...)` в тестах и превью
  задают только `entries` — меньше шаблонного кода.

**Альтернативы:**

- Хранить `sections` рядом с `entries` («производное, но согласованное»).
  Отказ: см. Decision 1 — производное в state не храним.

### Decision 3. Зона группировки — параметр с дефолтом, а не инъекция в ViewModel

`groupEntriesByDate(entries, zone: ZoneId = ZoneId.systemDefault())`
принимает зону параметром с дефолтом; рендерер вызывает функцию без
зоны. `MainViewModel` зону не принимает — сигнатура `factory(repository)`
и конструктор не менялись вовсе.

**Почему:**

- Граничные случаи группировки (запись за 23:59 вчера vs 00:01 сегодня)
  проверяются детерминированно в `EntryDateGrouperTest` с явно
  переданной зоной (`ZoneId.of("UTC")`), без привязки к настройкам
  машины и без инъекции в `MainViewModel`.
- Дефолт совпадает с продом: рендер-вызов без аргумента даёт
  системную зону устройства.

**Альтернативы:**

- Инъектировать `zone` в `MainViewModel` для тестов. Отказ: после
  переноса группировки на рендер параметр стал бы мёртвым — в VM
  не осталось ни одного использования (итог ревью: параметр удалён).
- Инъектировать `clock: () -> LocalDate` или `java.time.Clock` на
  уровне `MainViewModel`. Отказ: группировка от «сегодня» не зависит —
  секции определяются только датами записей, и источник текущей даты
  в ViewModel стал бы мёртвым параметром; заголовки секций резолвятся
  на рендере, а секция «Сегодня» заголовка вообще не имеет (Decision 5).

### Decision 4. Заголовок резолвится инлайном на рендере

В `EntryListItems` заголовок секции — выражение из одной строки:
`if (section.date == yesterday) yesterdayLabel else section.date.format(formatter)`,
где `yesterdayLabel` — `stringResource(R.string.entry_section_yesterday)`,
`formatter` — `remember { DateTimeFormatter.ofPattern("dd.MM.yyyy") }`,
`today`/`yesterday` — `remember { LocalDate.now() }` на входе
в композицию. Секция «Сегодня» заголовка не имеет — фильтруется
до этого выражения (Decision 5). Отдельная функция/файл не заводятся.

**Почему:**

- Ветка одна и вызов один: функция-обёртка с четырьмя параметрами
  была бы длиннее самого выражения на call-site (итог ревью —
  `SectionTitleFormatter` удалён).
- Локализация выполняется в composable через `stringResource(...)`;
  форматтер из stdlib отдельно не тестируется — контракт «ведущие
  нули в `dd.MM.yyyy`» — свойство `DateTimeFormatter`, а не нашего
  кода.

**Альтернативы:**

- Отдельная pure-функция `sectionTitle(...)` + JVM-тесты. Отказ:
  тестировался бы stdlib-форматтер, а не наш код; setup параметров
  длиннее тела.
- Передавать `Context` и `R.string.entry_section_yesterday` в функцию.
  Отказ: зависимость от Android там, где хватает `stringResource`
  в composable.

### Decision 5. `stickyHeader` из Compose Foundation, разные `contentType`

В `LazyColumn` используем
`androidx.compose.foundation.lazy.LazyListScope.stickyHeader { SectionHeader(...) }`
для заголовков секций, между ними — обычный `items(section.items, ...)`.
Секция «Сегодня» рендерится без заголовка: список открывается на
сегодняшних записях, sticky-хедер «Сегодня» дублирует очевидное и
съедает высоту. Условие `section.date != today` — в `EntryListItems`;
`today`/`yesterday` зафиксированы `remember` на входе в композицию.

`stickyHeader` — нативный DSL из Compose Foundation, отдельная
зависимость не нужна (уже подключена через `compose.foundation`).

Заголовки и строки получают разные `contentType`:

- заголовок (`stickyHeader`): `contentType = "section"` — значение
- строка (`items`): `contentType = { "row" }` — лямбда-фабрика

**Почему:**

- Compose внутри одной `LazyColumn` поддерживает раздельные пулы
  переиспользования по `contentType`: заголовок не вытесняет строку
  и наоборот — это снимает риск визуального «моргания» при скролле.
- `key` остаётся `it.id` (лямбда) для строк; для заголовков `key` —
  `section.date.toEpochDay()` (значение, не лямбда — стабильный,
  уникальный в пределах списка).

**Альтернативы:**

- Не использовать `contentType`. Отказ: без него Compose относит
  `SectionHeader` и `EntryListItemRow` к одному пулу и переиспользует
  composables друг в друга — визуальный артефакт при скролле.
- Подключать стороннюю библиотеку sticky-headers. Отказ: лишняя
  зависимость, нативный DSL достаточен.

## Risks / Trade-offs

- [Заголовок «Вчера» застывает на момент входа в композицию, а не
  тикает в полночь]
  → Группировка от «сегодня» не зависит — записи не переезжают между
    секциями при переходе через полночь; меняется только лейбл:
    при пересоздании композиции (возврат на экран) секция вчерашних
    записей получит заголовок-дату. Для типичного сценария
    использования это незаметно; явно устраивать таймер «тикать в
    полночь» избыточно (см. AGENTS.md — YAGNI).
- [Явная сортировка в `groupEntriesByDate` перед `groupBy`]
  → Списки тренировок в offline-only приложении — десятки/сотни
    записей, O(n log n) на список такого размера незаметен.
    Компромисс выбран сознательно (см. Decision 1 «Контракт
    группировки»): самодостаточность функции важнее микро-оптимизации.
    Если когда-либо понадобится, переход на single-pass с явной
    сортировкой внутри прохода локален.
- [Тесты `groupEntriesByDate` зависят от `ZoneId` — расхождение зон
  между продом и тестом]
  → Митигация: зона — параметр функции с дефолтом
    `ZoneId.systemDefault()` (совпадает с продом); JVM-тесты
    фиксируют зону детерминированно (`ZoneId.of("UTC")`).

## Migration Plan

Развёртывание — простой коммит, без миграций данных и без фичефлагов:

1. Добавить `EntryDateGrouper.kt`, `SectionHeader.kt` + JVM-тесты
   группировки.
2. Добавить строку в `strings.xml` / `values-en/strings.xml`.
3. Перевести `MainScreen` → `SuccessBody`/`EntryListItems` на цикл по
   секциям: `remember(entries) { groupEntriesByDate(entries) }`,
   `stickyHeader` + `items`, разные `contentType`; секция «Сегодня» —
   без заголовка.
4. Обновить `MainScreenPreview`, добавить androidTest на регрессию.

Откат — стандартный `git revert`. Поскольку модель данных, SQL и
`MainViewModel` не тронуты, откат не требует схемной миграции.
